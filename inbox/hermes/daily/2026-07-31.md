## 2. 主要工作

### 2.1 在线通知更新与在线图搜解耦

- 明确两个场景：在线通知更新需要校验商品权威类目与图片预测类目；在线图搜继续保持现有“图片向量判断上下装”的门禁。
- 代码调整坚持最小影响：通知链路可使用权威类目查询、二级类目预测以及 `shadow/enforce`，但不能改写在线图搜原有 SQL、队列合同和裁剪语义。
- 与 PHP 调用端完成同频：`/g/service/goods_image_vector_update_algorithm` 中的 `/g/` 是 GPU 网关前缀；业务只要求通知被服务接受，后续 GD、向量生成和写库属于异步职责。
- 当前代码链路和相关测试已闭合，但尚缺一次真实通知贯穿 ClickZetta、GPU、PG 类目向量和 YunQi 写入的端到端证据。
- 新表与复用旧表仍需按最新表结构最终定案。若复用 `dwd_field_text_vector`，必须以独立 `compare_field` 命名空间隔离通知二级类目数据，并确保在线图搜仅查询原 `cat_name` 数据。

### 2.2 新增 GD 原始检测接口

- 新增 `POST /service/gd_detection_algorithm`，支持 `request_id`、`image_url`、`cat_name`、`top_k`，返回模型名、原图尺寸及 Top-N 原图坐标检测框。
- 增加 `extra_labels`，允许在三级类目映射标签之外附加检测标签；限制最多 3 个，避免标签过多拖慢推理。
- 实测发现 `extra_labels=["girl"]` 未出现在响应中。根因不是参数未传入，而是初版复用了业务裁剪链路，`girl` 被人体门控当作辅助框过滤。
- 修复后，该独立接口直接返回 GroundingDINO 原始检测结果，不再经过裁剪、NMS 和人体门控；相关回归共 58 项通过。
- 影响面已隔离：在线通知、在线图搜和离线裁剪继续使用原业务裁剪链路，不改变结果。稳定环境尚未部署该修复，部署后需用原 curl 复测。

### 2.3 图片向量清洗范围确认

- 当前清洗脚本只处理“二级类目为上装、三级类目为短袖 T 恤、图片向量 Top-1 判为下装”的候选。
- `--max-records 0` 只表示跑完该候选集合，不会自动扩展到衬衫、卫衣、外套等全部上装。
- GD 使用 `t-shirt + topwear` 是为了提高短袖 T 恤的上装识别率，不会改变 SQL 数据源范围。

## 3. 值得沉淀

1. 新增“检测结果查询”接口时，不应直接复用“业务裁剪”后处理链路；原始检测框与业务主体框是两种不同契约。
2. 跨业务复用向量表的关键不是“同表还是分表”，而是数据命名空间、查询过滤和旧链路回归保护是否完整。
3. 异步通知接口的完成定义要与调用方一致：业务只要求成功投递时，不应额外引入完成回调或同步等待。
4. 代码链路闭合和单元测试通过不等于端到端跑通；涉及 ClickZetta、GPU、PG 和 YunQi 时必须保留真实请求及最终写入证据。
