今天的主线是推进 **极速换货从“提交后直接建工单”调整为“先建申请单、支付、人工审核后再建正式工单”**，涉及 `yishouapp`、`service-order`、`yishouos` 三个项目。工作从后端实现与联调核对，逐步深入到上线兼容、支付临界、库存预占、超时取消、结束退款和数据库最小化设计；经过多轮审计，方案由较重的五表架构收敛为复用既有业务表、仅保留一张精简库存预占表。

## 2. 主要工作

### 2.1 三项目后端实现与联调核对

- `service-order` 补齐申请列表 `user_handle_type=7/8` 严格筛选、正式工单 `exchange_type` 的读写、筛选、展示和防御校验。
- 极速申请审核生成正式工单时，根据 `user_handle_type=8` 写入 `exchange_type=1`；APP 工单详情同步返回该字段。
- `yishouos` 完成普通/极速筛选和展示，禁止客服新建极速工单或将普通工单切成极速，极速转其他类型前检查 ERP 配货状态。
- 相关 Go 定向测试、`go vet ./...`、PHP 7.0.28 语法检查和两仓 `git diff --check` 均取得通过结果；Go 全量测试仅受既有 RPC 示例依赖未启动及证书路径问题影响。

### 2.2 PRD 流程与上线兼容审计

- 梳理了 APP 提交、库存预占、申请单、支付、人工审核、工单生成、ERP、取消退款的完整状态流。
- 确认三个项目无法同时发布，因此新流量必须通过开关隔离，不能让先发布的服务改变线上旧极速换货行为。
- 最终只保留 `yishouapp` 准入开关 `fast_exchange_application_v2.enabled`；`service-order` 仅在完整收到 `request_id + request_item_id + reservation_id` 时识别为新流程，旧请求继续走原逻辑。
- 纠正超时口径：PRD 中“超时结束”指客服驳回后等待用户补资料超时，不是支付后待审核 30 分钟自动结束。

### 2.3 数据模型从五表方案收敛为最小方案

- 对五张候选新表逐一做删除测试，取消事件表、申请关系表、outbox、inbox，仅保留一张精简库存预占表。
- 申请、支付、正式工单继续复用既有 `service_applicant`、`service_order_exchange_ext`、`service_order_ext`。
- 库存预占按申请明细落一行，状态仅保留 `1=占用中`、`2=已释放`；同 SKU 整体校验后，按明细拆分普通/预售占用，便于单申请准确释放。
- 明确华为云日志可替代错误原因、重试次数等运维信息，但不能替代 gocron 扫描所需的待处理业务事实。
- 数据库仅做了只读结构核对，未执行 DDL/DML；发现代理数据库入口存在疑似路由或节点元数据不一致，发布前需要数据库侧确认。

### 2.4 支付、取消与退款链路最小化

- 不修改微信、支付宝等支付渠道协议，不新增支付类型，继续使用 `payment_type=19`。
- 保持原支付状态 `0=待支付、1=已支付、2=已取消`，撤回 `flow_version`、`PAYING` 和独立支付事件方案。
- 只适配极速换货业务层：允许新流程在只有 `applicant_id`、尚无 `service_order_id` 时支付；支付成功后先激活申请为待审核，正式工单延后至审核通过时创建。
- 支付成功同步调用 `service-order` 激活申请；同步失败时，由 gocron 扫描“扩展表已支付但申请仍为状态 9”的记录补偿。
- 超时取消改为逐项幂等处理，并让支付回调与批次取消复用同一把 Redis 锁，降低取消与迟到支付并发竞争。
- 已支付申请结束后的退款任务按“退款申请可追踪、扩展表退款记账成功、库存释放成功”三项校验收口；新增 gocron 方法默认每批 100 条。

## 3. 值得沉淀

1. **先做删除测试，再建表**：能从既有业务表稳定推导的事实，不应额外建立事件表、关系表或消费记录表。
2. **日志不能代替业务状态**：日志适合排障和告警，gocron 是否需要继续补偿仍必须由可查询、可幂等的业务事实决定。
3. **支付改造要划清边界**：流程变化只需要适配极速换货业务落点，不应扩大为支付渠道协议或通用回调重构。
4. **滚动发布必须显式兼容旧请求**：新流程不能只靠已有业务枚举识别，应使用新请求独有且完整的元数据组合。
5. **简化状态机需要承认故障窗口**：库存仅保留“占用中/已释放”两态后，异常窗口主要依赖分布式锁、日志告警和人工核对，不能宣称完全自动恢复。
6. **流程图必须区分相似超时**：未支付超时、客服驳回后补资料超时、支付后待审核并非同一业务分支。
