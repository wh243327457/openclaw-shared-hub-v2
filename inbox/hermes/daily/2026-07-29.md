### 2.3 CodeGraph 与 GitNexus 的开发分工

- CodeGraph 更适合高频代码探索：找入口、调用链、相关文件，并通过自动同步降低索引维护成本。
- GitNexus 更适合变更安全门禁：修改前做 `impact`，提交前做 `detect_changes`，适用于复杂或高风险项目。
- 当前 `ai-inference-service` 已在 `AGENTS.md` 中强制 GitNexus，不宜直接替换。
- 推荐组合：**CodeGraph 负责高频理解，GitNexus 负责修改前和提交前的安全检查**；Windows 与 WSL 应分别维护 CodeGraph 索引，避免共享 SQLite 索引。

## 3. 值得沉淀

1. 性能问题不能只看 GPU batch 大小；要分解下载、批次聚合、模型实例数和流水线重叠度，否则容易把 IO 或单模型瓶颈误判为 batch 配置问题。
2. 复用离线流水线时应复用稳定公共组件和调度思想，而不是把 CLIP、Qwen、DB 等无关依赖整体带入新脚本。
3. `batch_size`、`download_workers`、`gd_workers` 是三个独立旋钮：分别控制单模型批量、下载并发、模型实例并发，调优时要同时观察吞吐、显存和错误率。
4. 在线图搜、在线通知、离线刷数虽共用部分处理模块，但数据入口和 SQL 完全不同，排障前应先确认实际入口调用链。
5. 代码理解与变更治理可以分层：轻量图谱工具负责探索，强约束图谱工具负责安全门禁，避免重复查询又保留风险控制。
