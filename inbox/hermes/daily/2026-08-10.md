### 2.3 跨 Agent `requirement-test` Skill 设计与落地

已明确跨 Agent 结构：

- `.agents/skills/requirement-test/` 作为 Codex、Cursor 的唯一主实现源。
- Claude Code 仅保留薄命令适配器，避免复制流程与脚本。
- `SKILL.md` 只规定参数、流程、门禁、完成条件与汇报格式。
- Python 脚本负责快照冻结、计划校验、Robot 执行、证据收集和报告生成。
- Agent 只能把自然语言步骤映射到已批准 Capability，不得临时编造 selector、代码、断言或修改预期结果。

今日已推进的核心能力与门禁：

- 冻结用例快照、manifest 和内容哈希；统一 UTF-8 + LF，消除 Windows CRLF / Linux LF 导致的跨平台哈希差异。
- 渲染受快照哈希、能力目录和 PageModel 约束的 planning prompt。
- 校验需求 ID、快照哈希、用例覆盖、能力名称、参数类型和运行 profile。
- 未知能力或 Agent 主动声明能力缺口时，生成 `capability-gap.json` 并以 `BLOCKED` 终止。
- 业务数据写入必须同时满足 `governed-write` 策略与显式授权，否则生成 `policy-block.json`。
- 校验阶段记录能力目录哈希，执行前复核，防止计划验证后偷渡 Robot keyword。
- Robot 执行器只消费 `validated-plan.json`，区分业务失败与平台失败；报告以 `output.xml` 为权威源，产出 `run-result.json` 与 HTML 报告。
- 默认 Baserow 数据源按数据库名、表名动态发现，不硬编码 table ID；`prepare` 支持主机只读拉取，`run` 保持离线快照可复现。
- 缺数据场景正在收口为 `NEEDS_CONFIRMATION`，要求生成事实快照和终止报告，不伪造测试用例。

截至采集时，多个阶段契约已通过单测，Docker 内主流程用例曾实际返回 `1 passed`；但缺数据场景和最终全量回归仍在继续收口，尚不应宣称整个 Skill 已完成验收。

### 2.4 WSL / Docker 验证问题

- Docker daemon 启动后会按 restart policy 拉起多组本地服务，造成初期 API 调用和测试超时。
- 测试本身曾在容器内约 5 秒通过，但外层 WSL 因 systemd user session 无法正常结束而返回超时码，不能直接把外层超时当成测试失败。
- 通过临时 WSL keepalive 稳定发行版生命周期后，主流程测试获得真实退出码 0。
- 这说明端到端验收需要同时记录“容器内测试结果”和“外层 WSL/进程退出状态”，避免误判。

## 3. 值得沉淀

1. **跨 Agent Skill 应只有一个主实现源。** Agent 之间只做薄入口适配，底层脚本、契约和产物格式必须共享，否则很快产生行为漂移。
2. **Skill、Agent、脚本职责必须分离。** Skill 管规范，Agent 做受限语义映射，脚本负责确定性执行与验收；未知能力宁可 `BLOCKED`，也不能临时生成浏览器代码。
3. **跨 OS 内容哈希必须先规范化。** 文本统一 UTF-8 + LF 后再计算哈希，避免 CRLF/LF 让同一快照在 Windows 与 Linux 上产生不同身份。
4. **流程完成与业务通过是两套状态。** 即使业务判定为 `PRODUCT_FAIL`，只要执行证据和报告完整，流水线仍可标记为 `verified`。
5. **写入稳定环境必须是双重授权。** 策略声明和运行时显式授权缺一不可，并要求测试数据、基线与回滚信息可验证。
6. **外层超时不等于内层失败。** WSL、Docker、pytest、Robot 各层退出状态应分开记录，先定位卡点再重跑。
