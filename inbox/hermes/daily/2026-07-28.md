## 1. 今日概览

今天的主线集中在 **商品图片向量库清洗与 GD 裁剪链路优化**。工作从异常图片筛选方案，推进到类目门禁修正、GD 二次识别与批量 Shadow 脚本，并进一步定位了本地 PG 字段、批处理性能及多图床裁剪参数兼容问题。

## 2. 主要工作

### 2.1 图片向量库清洗方案收敛

- 目标是从上装图片向量库中找出“图片实际只有短裤、牛仔裤等下装”的异常数据。
- 方案收敛为：先用图片向量与类目向量做候选筛选，再用 GD 二次识别区分“纯下装异常图”和“全身照中仍含上装的可修复图”。
- 清洗与在线链路被拆为两个功能面：
  1. 存量向量库清洗；
  2. 图片向量更新、在线图搜、离线刷数中的 GD 裁剪优化。
- 当前采取安全策略：只读查询、结果先落文件，不直接更新数据库；待人工分析后再决定是否入库。

### 2.2 类目门禁与 GD 裁剪优化

- 通过本地图片实测发现，部分明显上装图片会被类目门禁拦截，问题与类目标识及匹配粒度有关。
- 门禁判断已改为使用 `topwear` 标识；相关代码验证通过，共 `69 passed`。
- GD 策略重点聚焦上装、下装：有模特或全身框时优先选择更符合目标品类的局部框；套装等类别保持原流程，避免全局改动扩大影响面。
- 对 GD 未识别、裁剪后类目发生变化、裁剪后无变化的数据分别输出，便于后续抽样复核和阈值调整。

### 2.3 Shadow 跑批链路与性能

- 批处理链路围绕“SQL 候选 → GD 检测/裁剪 → 图片及文本向量 → 文件结果”推进，暂不写库。
- 初版逐张检测过慢，后续改为批量推理，并配置多个 GD worker；当前默认方向为 `2` 个 GD worker，每个 worker 内按 batch 处理。
- 实现优先复用已有离线刷数能力，同时避免修改公共逻辑而影响既有离线任务。
- 运行中暴露两类环境问题：容器环境变量已注入但不存在 `.env` 文件；本地类目向量查询 SQL 引用了实际表中不存在的字段条件，需要以真实表结构为准继续验收。

### 2.4 多图床裁剪参数兼容

- 实测发现，华为云 OBS 地址上的 `x-image-process` 裁剪参数有效，而 `img4.yishouapp.com` 不能直接复用同一种参数格式。
- 七牛类图床应按自身的 `imageView2` 规则拼接精确裁剪参数；不同来源需要分流处理，不能统一套用 OBS 参数。
- 将 `img4` 地址改写为直连 OBS 后，公共 HTTPS 可得到预期裁剪尺寸；但现有下载器可能因此进入 OBS SDK 路径，缺少 SDK、凭据或网络条件时会失败。
- 下一步应保留“源站专属参数 + OBS SDK 优先 + 公共 HTTPS 回退”的兜底设计，并在真实 GPU 容器验证。

## 3. 值得沉淀

1. **先 Shadow、后入库**：清洗型任务先输出候选、更新、异常结果文件，经抽样复核后再做数据库更新。
2. **向量筛选与视觉复核分层**：向量适合缩小候选集，GD/视觉模型适合判断全身图、局部服饰等复杂边界，二者不应互相替代。
3. **批处理要复用成熟链路**：优先复用离线刷数的批量推理与资源调度，不为一次性脚本重复构建单图串行流程。
4. **图床参数必须按源适配**：OBS、七牛及 CDN 域名的裁剪语法和下载路径不同，既要验证尺寸，也要验证运行容器的 SDK/凭据与回退路径。
5. **数据库字段以运行环境为准**：SQL 条件必须通过真实表结构或只读探针验证，不能仅依赖仓库内旧 SQL 或字段命名推断。
