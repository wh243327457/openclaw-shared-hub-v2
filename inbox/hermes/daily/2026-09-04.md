### 2.2 库存安全测试基准升级

原有“最终库存不超过测试前基线”不能证明没有重复恢复：正常订单同期消耗库存时，多恢复可能被掩盖。测试门禁已改为以不可变预占明细为核心的守恒约束：

1. 每个 `request_item_id × SKU × 库存来源` 的累计成功恢复量，不得超过首次实际成功扣减量。
2. 申请仍有效或库存已转交正式工单时，申请侧恢复量必须为 0。
3. Redis/DB 结果未知时禁止盲目再次恢复，宁可暂时少恢复并进入告警、对账。
4. 审核建单、取消、支付、超时、库存同步/重建等并发下，不得出现“有效正式工单 + 预占已释放”或临时虚假可售库存。

### 2.5 向量通知 503 诊断

- 当前证据不支持“24G 显存不足就是 503 的直接原因”。`livez=200`，但 `/g/service/readyz` 持续超时，通知请求尚未进入更新子服务的 `batch_predict`，更像 BentoML 依赖子服务未就绪、进程异常或网关无健康上游。
- 24G 是真实放大因素：单副本至少重复加载 `2×GroundingDINO + 2×CLIP`，跨进程锁又不能控制同卡总并发；历史上出现过显存接近耗尽的 CUDA OOM。
- 受控配置 `HTTP 并发4 + 每批10图 + GD并发1` 曾实现 500/500 成功，说明 24G 并非天然不可用。
- 优先级应是：恢复 readiness → 核对子服务 OOM/重启/PID 显存 → 固定已验证并发 → 降低下载并发或拆线程池 → 隔离/复用模型服务 → 对齐各层超时。
- 相关入口与批处理测试共 `68 passed`，本轮只读诊断，未修改文件。

### 2.6 账号令牌安全

- 已明确：`access_token` 不能直接填入 ChatGPT 官方登录页，但泄露后仍可能被脚本或非官方客户端在有效期内滥用。
- 安全处置顺序为：退出所有设备、修改登录凭证、开启 MFA、检查陌生设备/会话；若泄露的是 API key，则必须单独删除旧 key 并检查 Usage。

## 3. 值得沉淀

- **复杂需求先治理事实，再推进实现。** PRD、用户决策、源码现状和 AI 假设必须分层记录，已关闭问题不能无证据重开。
- **库存安全要按事件与所有权守恒验收。** 总库存最终值不能替代逐预占、逐库存键的恢复核算。
- **结果未知时必须 fail-closed。** 涉及库存、资金、状态终态时，不能因网络异常直接重试副作用。
- **健康检查要区分 live 与 ready。** 进程存活不代表依赖可服务；503 应先定位由业务、代理、readiness 还是进程退出产生。
- **成功统计必须区分完整成功与部分成功。** 否则后置安全步骤失败会被“成功数”掩盖。
