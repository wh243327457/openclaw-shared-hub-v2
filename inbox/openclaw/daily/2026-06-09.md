## 深读项目

### 1. JimLiu/baoyu-design

**一句话判断**：把 Claude Design（claude.ai/design 的设计引擎）封装成可本地运行的 Agent Skill，让 Cursor、Claude Code、Codex 等本地 Agent 直接产出高质量 UI 原型。

**解决的问题**：以前要用 Claude Design 必须访问 claude.ai 网站，设计产物留在平台上。baoyu-design 把整个设计方法论（clarify → gather context → produce HTML → preview → verify）打包成 Markdown skill，本地 Agent 加载后即可执行，产物是自包含 HTML，留在自己 repo 里。

**架构/实现**：
```
skills/baoyu-design/
├── SKILL.md              # 入口 — 编排整个设计流程
├── system-prompt.md      # 设计方法论 & 工艺标准（核心真相源）
├── references/
│   ├── claude.md         # Claude Code 工具映射
│   ├── cursor.md         # Cursor 工具映射
│   └── codex.md          # Codex Agent 工具映射
├── built-in-skills/      # 24 个专项提示（decks、mobile、export…）
└── starter-components/   # 设备框架、deck stage、canvas、动画引擎
```

核心设计模式：
- **Harness-adaptive**：skill 检测运行环境（Cursor/Claude Code/Codex），加载对应的工具映射文档
- **Progressive disclosure**：SKILL.md 保持精简，深入指导按需加载
- **Deliverable = HTML**：所有产出都是自包含 HTML，可通过 localhost preview 实时迭代

**关键源码文件**：
- `skills/baoyu-design/SKILL.md` — 入口文件，定义设计流程编排
- `skills/baoyu-design/system-prompt.md` — 设计方法论核心，包含工艺标准和质量要求
- `skills/baoyu-design/built-in-skills/` — 24 个专项 skill（hi-fi design、prototype、wireframe、deck、mobile、export 等）
- `skills/baoyu-design/starter-components/` — iOS/Android/macOS 浏览器框架、pan-zoom canvas、slide-deck stage、timeline 动画引擎

**最小运行验证路径**：
1. `npx skills add JimLiu/baoyu-design` 安装到当前项目
2. 在 Cursor/Claude Code 中打开项目
3. 输入 "Design a settings screen for a meditation app"
4. Agent 加载 SKILL.md → 读取 system-prompt.md → 执行设计流程
5. 在 localhost preview 中查看产出的 HTML 原型

**可迁移设计模式**：
1. **当需要把平台能力本地化时，应优先用 Markdown skill 封装方法论而非重写引擎**，因为 skill 只需定义流程和标准，Agent 本身已有执行能力，边界是 skill 依赖的工具必须在目标环境中可用
2. **当需要支持多个 Agent 平台时，应优先用 references/ 目录做 harness-specific 工具映射**，因为核心逻辑保持平台无关，每个平台只需一个映射文件，边界是映射文件需要随平台 API 变化更新
3. **当设计产物需要可迭代时，应优先输出自包含 HTML 而非截图或 PDF**，因为 HTML 可以被 Agent 的 preview 工具直接渲染并支持元素级标注修改，边界是复杂交互可能需要本地服务器

**可复用经验**：
- Agent Skill 的架构模式：SKILL.md（入口）+ system-prompt.md（方法论）+ references/（平台映射）+ built-in-skills/（专项能力）
- 本地化 vs 平台化的权衡：选择本地化时，把"方法论"而非"引擎"作为迁移单元
- 渐进式加载策略：skill 保持精简，深入内容按需加载，降低 token 消耗

**风险边界**：
- 最佳效果依赖 Claude Opus 4.8，其他模型产出质量可能下降
- 24 个 built-in skill 的质量未经独立验证
- 无自动化测试，依赖人工验证产出质量
- MIT license，可自由使用和修改

**Skill 升格判断**：
**判断**：可直接迁移

可直接迁移的部分：
1. Skill 架构模式（SKILL.md + system-prompt.md + references/）可直接用于 Hermes 的 skill 设计
2. harness-adaptive 模式可借鉴用于 Hermes 支持多 Agent 平台

需要二次验证的部分：
1. 24 个 built-in skill 的具体内容需要逐个审查质量
2. starter-components 的兼容性需要在目标环境中测试

暂不沉淀的部分：
1. 具体的设计方法论（system-prompt.md 的内容）— 这是 Claude Design 的专有知识

**候选反哺**：
- candidate fact: "Agent Skill 架构模式：入口 SKILL.md + 方法论 system-prompt.md + 平台映射 references/ + 专项能力 built-in-skills/"
- candidate skill-workflow: "harness-adaptive skill 设计模式 — 检测运行环境，加载对应工具映射"

### 2. tastyeffectco/sandboxd

**一句话判断**：开源自托管 Agent 沙箱引擎，一条命令启动，每个用户一个隔离容器，自带 AI 编码 Agent 和实时预览 URL。

**解决的问题**：构建 AI app-builder（"描述一个 app → 看到它运行"）时，最难的不是 prompt，而是底层基础设施：容器隔离、网络路由、sleep/wake、持久化。sandboxd 把这些打包成一个 Go 二进制 + Docker + Traefik + SQLite 的最小栈。

**架构/实现**：
```
┌──────────────── your host (just needs Docker) ────────────────┐
 browser ──▶│  Traefik  ──▶  sandbox  (coding agent + dev server :3000)      │
            │     ▲              ▲   ▲                                        │
 API/CLI ──▶│  sandboxd ─────────┘   └─ workspace dir (persists)             │
            │     │  SQLite (source of truth) · idle→stop · request→wake      │
            └─────┴────────────────────────────────────────────────────────-─┘
```

核心模块：
- `control-plane/cmd/sandboxd/` — 主入口，HTTP API 服务器
- `control-plane/internal/docker/` — Docker 容器管理
- `control-plane/internal/traefik/` — Traefik 动态路由配置
- `control-plane/internal/wake/` — sleep/wake 机制
- `control-plane/internal/snapshot/` — 快照管理
- `control-plane/internal/store/` — SQLite 数据层
- `control-plane/migrations/` — 10 个数据库迁移

**关键源码文件**：
- `control-plane/cmd/sandboxd/main.go` — 主入口
- `control-plane/internal/docker/` — Docker 容器生命周期管理
- `control-plane/internal/wake/` — 空闲检测 + 唤醒逻辑
- `control-plane/internal/traefik/` — 动态路由配置生成
- `control-plane/migrations/` — 数据库 schema
- `image/Dockerfile` — 沙箱镜像定义（预装 OpenCode、Claude Code CLI）
- `docker-compose.yml` — 一键部署配置

**最小运行验证路径**：
1. `git clone https://github.com/tastyeffectco/sandboxd && cd sandboxd`
2. `docker compose up -d` 启动 Traefik + sandboxd
3. `curl -X POST http://localhost:8080/sandbox` 创建沙箱
4. 记录返回的 sandbox ID
5. `curl -X POST http://localhost:8080/sandbox/<id>/tasks -d '{"prompt":"build a todo app"}'` 触发 Agent 编码
6. 访问 `http://<id>.preview.localhost` 查看实时预览

**可迁移设计模式**：
1. **当需要为多用户提供隔离执行环境时，应优先用 Docker 容器 + Traefik 动态路由而非 Kubernetes**，因为单机部署足够支撑中等规模用户，运维复杂度低一个数量级，边界是超过单机容量时需要迁移到 K8s
2. **当沙箱需要省钱时，应优先实现 sleep/wake 机制而非一直运行**，因为空闲容器占用内存但不产生价值，wake 机制让单机可以支撑更多用户，边界是 wake 延迟会影响用户体验
3. **当需要持久化沙箱状态时，应优先用 workspace 目录挂载而非容器内存储**，因为容器销毁时数据不丢失，边界是磁盘 I/O 可能成为瓶颈

**可复用经验**：
- Agent 沙箱的最小栈：一个 Go 二进制 + Docker + Traefik + SQLite，无 K8s、无消息队列
- Sleep/wake 模式：空闲检测 → stop 容器 → 请求到达 → wake → 恢复状态
- 沙箱镜像预装 Agent CLI（OpenCode、Claude Code），开箱即用

**风险边界**：
- Beta 阶段，生产环境需谨慎
- 单机架构有上限，大规模部署需要额外工程
- 无 license 信息（meatshell），需确认使用条款
- Traefik 依赖增加了部署复杂度

**Skill 升格判断**：
**判断**：需二次验证

可直接迁移的部分：
1. Sleep/wake 机制的设计思路可借鉴用于 Hermes 的沙箱管理
2. SQLite 作为轻量级状态存储的模式

需要二次验证的部分：
1. 实际性能表现（单机支撑多少并发沙箱）
2. 与现有 Docker 基础设施的兼容性

暂不沉淀的部分：
1. 具体的 API 设计 — 需要根据 Hermes 的实际需求定制

**候选反哺**：
- candidate fact: "Agent 沙箱最小栈：Go + Docker + Traefik + SQLite，无 K8s"
- candidate skill-workflow: "sleep/wake 沙箱管理机制 — 空闲检测、stop、请求唤醒、状态恢复"
- open question: "sandboxd 的 sleep/wake 机制是否可以用于 Hermes 的 OpenClaw 容器管理？"

### 3. amElnagdy/guard-skills

**一句话判断**：给编码 Agent 加质量门禁的 skill 包，5 个 guard 分别捕获 AI 生成代码、测试、文档、WordPress、WooCommerce 的系统性失败模式。

**解决的问题**：AI 编码 Agent 有系统性的失败模式：过度抽象、吞掉错误、mock 滥用、文档幻觉、WordPress 安全漏洞。guard-skills 不是教 Agent 如何写代码，而是在 Agent 写完后做二轮审查，用明确的规则集捕获这些模式。

**架构/实现**：
```
skills/
├── clean-code-guard/     # 通用代码质量（SOLID、DRY/KISS/YAGNI + AI 特有层）
│   ├── SKILL.md
│   ├── agents/openai.yaml
│   └── references/
│       ├── ai-failure-modes.md    # AI 代码的系统性失败模式
│       ├── solid.md               # SOLID 原则检查
│       ├── dry-kiss-yagni.md      # DRY/KISS/YAGNI 检查
│       ├── naming-and-functions.md # 命名和函数设计
│       ├── comments-and-formatting.md # 注释和格式
│       └── review-checklist.md    # 审查清单
├── test-guard/           # 测试质量（mock 滥用、重复测试、实现细节断言）
├── docs-guard/           # 文档准确性（幻觉符号、断开的示例、文档-代码漂移）
├── wp-guard/             # WordPress 安全（转义、sanitization、nonce、prepared queries）
└── woo-guard/            # WooCommerce 安全（HPOS、CRUD vs meta、checkout 验证）
```

核心设计：
- **Reactive review**：Agent 完成工作后，在 diff 上运行 guard
- **Progressive disclosure**：SKILL.md 精简，深入规则按需加载
- **AI-specific layer**：除了通用 clean code 规则，还捕获 AI 特有的失败模式（过度抽象、吞错误、硬编码成功返回、幻觉 API）

**关键源码文件**：
- `skills/clean-code-guard/SKILL.md` — 通用代码质量门禁入口
- `skills/clean-code-guard/references/ai-failure-modes.md` — AI 代码系统性失败模式研究
- `skills/test-guard/SKILL.md` — 测试质量门禁（9 条通用规则）
- `skills/docs-guard/SKILL.md` — 文档准确性门禁
- `skills/wp-guard/SKILL.md` — WordPress 安全门禁
- `skills/woo-guard/SKILL.md` — WooCommerce 安全门禁

**最小运行验证路径**：
1. `npx skills add amElnagdy/guard-skills` 安装全部 guard
2. 在 Claude Code 中让 Agent 写一个函数
3. 输入 "Use $clean-code-guard on the diff you just produced"
4. Agent 加载 SKILL.md → 按规则审查 → 输出问题列表和修复建议
5. 检查输出是否捕获了 AI 特有的失败模式

**可迁移设计模式**：
1. **当需要给 Agent 加质量门禁时，应优先用 reactive review 而非 inline constraints**，因为 review 在 Agent 完成工作后执行，不干扰生成过程，捕获率更高，边界是需要 Agent 支持 skill 加载
2. **当审查规则需要覆盖多个领域时，应优先用独立的 guard skill 而非一个巨型规则文件**，因为每个 guard 可以独立安装和更新，按需组合，边界是 guard 之间可能有重叠
3. **当需要捕获 AI 特有失败模式时，应优先参考已发表的研究（如重复增长、包幻觉）而非凭经验**，因为研究提供了系统性的分类和量化数据，边界是研究可能滞后于模型能力变化

**可复用经验**：
- Guard skill 架构：SKILL.md（入口）+ references/（规则详情）+ agents/（平台元数据）
- AI 代码的 6 大失败模式：catch-all 吞错误、硬编码成功返回、幻觉 API、过度抽象、注释污染、copy-from-similar
- 测试质量的 9 条通用规则：mock 只在系统边界、不要 mock 自己的状态对象、参数化而非复制粘贴

**风险边界**：
- Guard 质量依赖规则的准确性，需要持续维护
- 无自动化测试验证 guard 的捕获率
- WordPress/WooCommerce guard 只适用于特定技术栈
- 需要 Agent 支持 skill 加载机制

**Skill 升格判断**：
**判断**：可直接迁移

可直接迁移的部分：
1. Guard skill 架构模式可直接用于 Hermes 的代码审查 skill
2. AI 失败模式研究可直接用于 Hermes 的审计流程
3. clean-code-guard 的规则集可直接用于 Hermes 的代码质量检查

需要二次验证的部分：
1. 9 条测试规则的完整内容需要逐条审查
2. WordPress/WooCommerce guard 的适用性需要评估

暂不沉淀的部分：
1. agents/openai.yaml 的具体内容 — 这是 OpenAI Codex 的元数据格式

**候选反哺**：
- candidate fact: "AI 代码 6 大失败模式：catch-all 吞错误、硬编码成功返回、幻觉 API、过度抽象、注释污染、copy-from-similar"
- candidate skill-workflow: "Reactive review guard 模式 — Agent 完成工作后，用独立 guard skill 做二轮审查"
- candidate fact: "Guard skill 架构：SKILL.md + references/ + agents/，渐进式加载"
- open question: "guard-skills 的 clean-code-guard 规则是否可以整合到 Hermes 的 requesting-code-review skill？"

## 经验沉淀/可复用经验

1. **Agent Skill 架构三件套**：SKILL.md（入口编排）+ system-prompt.md/references/（方法论/规则详情）+ built-in-skills/（专项能力）。当需要封装一个复杂能力为 Agent Skill 时，应优先用这个三件套结构，因为入口精简降低 token 消耗，深入内容按需加载。来自：baoyu-design

2. **Reactive Review > Inline Constraints**：当需要给 Agent 加质量门禁时，应优先在 Agent 完成工作后用独立 guard 做二轮审查，而非在生成时加约束。因为 review 不干扰生成过程，且可以引用已发表的失败模式研究。来自：guard-skills

3. **Agent 沙箱最小栈**：当需要为多用户提供隔离执行环境时，应优先用 Go + Docker + Traefik + SQLite 的最小栈，而非 Kubernetes。因为单机部署足够支撑中等规模，运维复杂度低一个数量级。来自：sandboxd

4. **Harness-adaptive Skill 设计**：当一个 skill 需要支持多个 Agent 平台时，应优先用 references/ 目录做平台特定工具映射，核心逻辑保持平台无关。来自：baoyu-design
