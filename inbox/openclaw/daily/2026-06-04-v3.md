### 1. chopratejas/headroom

**一句话判断**：本地运行的上下文压缩中间层，为 AI Agent 的 tool 输出/日志/RAG chunk/对话历史提供 60-95% 的 token 削减，通过 CCR（Compress-Cache-Retrieve）机制保留原文可逆检索。Python + Rust 混合架构。

**解决的问题**：LLM Agent 执行任务时产生大量 token 消耗（tool 输出 JSON 数百行、日志、搜索结果、代码文件）。这些内容直接发给 LLM 浪费 token 且稀释注意力。Headroom 在 prompt 到达 LLM 之前自动压缩，保留语义关键信息，丢弃冗余。

**架构/实现**：
- 核心模块：
  - `compress.py` — 一行 API 入口 `compress(messages)`
  - `pipeline.py` — 11 阶段生命周期 + Protocol 扩展
  - `transforms/` — 压缩器矩阵：SmartCrusher(JSON/Rust)、CodeCompressor(AST/tree-sitter)、Kompress-base(text/ML ONNX)、LogCompressor、SearchCompressor、DiffCompressor、HTMLExtractor
  - `ccr/` — 可逆压缩：注入 sentinel + 原文存储 + `headroom_retrieve` 工具
  - `memory/` — 跨 Agent 记忆（Qdrant/SQLite-vec）
  - `providers/` — Claude/Codex/Copilot/OpenClaw 适配
  - `proxy/` — FastAPI 透明代理
  - `crates/` — Rust 核心（headroom-core → PyO3 绑定）
- 数据流：`messages[] → CacheAligner → ContentRouter → 压缩器们 → 输出`
- 四大接入模式：Library / Proxy / Agent wrap / MCP Server

- 核心：`tiktoken`（token 计数）、`pydantic`（配置）、`litellm`（模型注册）、`click+rich`（CLI）
- 可选：`[proxy]` FastAPI+uvicorn+onnxruntime、`[code]` tree-sitter、`[ml]` torch+HuggingFace

- 风险：`litellm==1.82.3` 精确锁定可能冲突；Rust 构建链需要 toolchain

**可复用经验**：
1. **当需要压缩 LLM 上下文时，应优先采用 ContentRouter 模式**（检测内容类型→选择压缩器→重组），因为不同类型内容（JSON/代码/日志/文本）需要不同压缩策略，统一路由比一刀切压缩效果好 3-5 倍
2. **当压缩会丢失信息时，应优先采用 CCR 可逆压缩**（压缩时存原文+注入 sentinel，LLM 按需取回），因为纯丢弃会导致 LLM 需要原文时无法恢复，CCR 让压缩率和信息完整性不再矛盾
3. **当 Python 热路径性能不足时，应优先用 Rust+PyO3 替代**（保留 Python API 兼容性），因为 maturin 构建的 PyO3 扩展可以无缝替换 Python 函数，用户无感知

**可尝试实验（≤30 min）**：
`pip install headroom-ai` → `from headroom import compress` 在 Hermes agent 中试压缩 tool 输出 → `headroom perf` 查看压缩率

**风险边界**：
- **License**: Apache-2.0，可商用
- **维护活跃度**: 11K+ stars，今日 +3,139，爆发期
- **安全风险**: CCR 原文存储有 TTL 但默认不清除；proxy 模式需信任 headroom 进程
- **不适用场景**: 需要精确 token 级控制的场景；纯文本无结构化内容压缩收益低

**⭐ Skill 升格判断**：**需二次验证** — 作为运行时依赖集成（`pip install`），不需要升格为 skill。如果将来做"上下文压缩"共享能力，可封装 `compress()` 调用逻辑。

```python
# 文件: utils/embedding.py — 长文本自动分 chunk + 均值池化
async def generate_embedding(text: str, ...) -> List[float]:
    text_tokens = token_count(text)
    if text_tokens <= CHUNK_SIZE:
        return (await generate_embeddings([text]))[0]
    # 长文本: 分 chunk → 批量嵌入 → 均值池化为单向量
    chunks = chunk_text(text, content_type=content_type, file_path=file_path)
    embeddings = await generate_embeddings(chunks)
    return await mean_pool_embeddings(embeddings)

async def mean_pool_embeddings(embeddings: List[List[float]]) -> List[float]:
    arr = np.array(embeddings, dtype=np.float64)
    norms = np.linalg.norm(arr, axis=1, keepdims=True)
    normalized = arr / np.where(norms > 0, norms, 1.0)  # L2 归一化
    mean = np.mean(normalized, axis=0)                   # 均值
    mean_norm = np.linalg.norm(mean)
    return (mean / mean_norm if mean_norm > 0 else mean).tolist()  # 再归一化
```

```python
# 文件: ai/provision.py — 智能模型选择
async def provision_langchain_model(content, model_id, default_type, **kwargs):
    tokens = token_count(content)
    if tokens > 105_000:
        model = await model_manager.get_default_model("large_context", **kwargs)
    elif model_id:
        model = await model_manager.get_model(model_id, **kwargs)
    else:
        model = await model_manager.get_default_model(default_type, **kwargs)
    return model.to_langchain()
```

```go
func run(ctx context.Context, opts flag.Options, targetKind TargetKind) (types.Report, error) {
    r, err := NewRunner(ctx, opts, targetKind) // 初始化DB/WASM模块
    defer r.Close(ctx)

    scans := map[TargetKind]func(...) (types.Report, error){
        TargetContainerImage: r.ScanImage,
        TargetFilesystem:     r.ScanFilesystem,
        TargetRepository:     r.ScanRepository,
        TargetSBOM:           r.ScanSBOM,
        TargetVM:             r.ScanVM,
    }
    // 三步流水线：Scan → Filter → Report
    report, err := scans[targetKind](ctx, opts)
    report, err = r.Filter(ctx, opts, report)
    err = r.Report(ctx, opts, report)
    return report, nil
}
```

**可复用经验**：
1. **当需要支持多种扫描目标时，应优先抽象统一的 Artifact 接口**（Inspect→Scan→Clean），因为 5 种目标类型（镜像/文件系统/仓库/SBOM/VM）共享同一扫描流水线，新增目标只需实现接口
2. **当需要 100+ 插件自动发现时，应优先用 blank import 的 `all` 包注册制**（`import _ "xxx/all"`），因为零耦合、编译时确定、不需要运行时配置
3. **当需要多数据源 severity 时，应优先建立明确的优先级回退链**（数据源→GHSA→NVD→兜底），因为不同数据源的覆盖率和准确度不同，有明确优先级才能保证每个 CVE 都有合理等级

## 经验沉淀

1. **当需要压缩 LLM 上下文时，应优先按内容类型路由到不同压缩器**（headroom 的 ContentRouter 模式），因为 JSON/代码/日志/文本的压缩策略差异很大，统一路由比一刀切效果好 3-5 倍。边界：压缩率 > 90% 时语义损失风险增大。

2. **当构建 RAG 系统时，应优先让 LLM 自行规划多个搜索词再并行执行**（open-notebook 的 ask.py 模式），因为 LLM 对问题的理解比关键词提取更精准，fan-out 并行比串行检索召回率高。边界：搜索词 > 5 个时 token 成本线性增长。

3. **当需要支持 100+ 扩展时，应优先用 blank import 注册制 + WASM 插件双层架构**（trivy 的 analyzer 注册 + module 系统），因为 blank import 保证编译时确定性，WASM 保证运行时安全隔离。边界：WASM 性能比 native 慢 2-5x。

4. **当 Python 热路径性能不足时，应优先用 Rust+PyO3 替代而非重写**（headroom 的 SmartCrusher），因为 maturin 构建的 PyO3 扩展可以无缝替换 Python 函数，用户 API 零改动。边界：需要 Rust toolchain + maturin 构建链。

5. **当 embedding 文本超过模型限制时，应优先用"分 chunk + L2 归一化 + 均值池化"**（open-notebook 的 embedding.py），因为归一化后均值池化保证输出向量是单位长度，无论 chunk 数量多少。边界：chunk 语义差异大时均值会模糊关键信息。
