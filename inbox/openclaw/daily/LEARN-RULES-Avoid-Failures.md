# OpenClaw GitHub 学习质量规则 — 来自历史审计的失败教训

> 本文件由 Hermes 基于历史审计失败记录总结。  
> OpenClaw 每次执行 GitHub 热门项目学习前，必须先阅读本文件并确认所有规则已遵守。

---

## 一、报告结构完整性（最高频失败点）

### R1. 深读项目必须有完整的六个章节

每次学习必须对至少一个候选项目做深读，且**必须包含全部六节**，不得截断：

| 章节 | 必须包含的内容 | 常见错误 |
|------|--------------|---------|
| C1. 核心命令 | README 中的安装/运行命令，标注 OS 要求 | 只写一行安装命令就结束 |
| C2. Repo Tree 摘要 | 目录结构 + 每层用途说明，用等宽字体展示 | 截断在某个子目录名处 |
| C3. 关键源码文件 | 列表形式，含文件路径、用途、关键内容摘要 | 缺少此节 |
| C4. 最小运行验证路径 | 5 步以内可完成的验证命令序列 | 只有安装命令，无验证步骤 |
| C5. 可迁移设计模式 | 至少 3 条可复用的工程模式，附我们的工作流如何落地 | 无此节，或仅抄 README 自述 |
| C6. 风险边界 | 至少 3 条已知限制、风险或需二次验证的点 | 无此节 |

**截断判定**：如果文件在 C2 之后出现 `…` 或戛然而止，该报告直接不合格。

### R2. 候选表必须包含全部七列

```
# | owner/repo | source_url | stars | language | license | created_at | pushed_at | why_selected
```

其中：
- `stars`、`license`、`created_at`、`pushed_at` 必须是**实时 GitHub API 查询值**，不得引用历史数字或估算
- `why_selected` 必须有**实质性判断**，禁止泛泛描述（如"很火""值得关注"）
- `license` 为 `null` 时必须标注"无license或proprietary"，不得留空

## 二、事实准确性与可验证性

### R3. 所有数字必须标注来源和查询时间

每份报告开头必须有一张"抓取口径表"：

```
| 查询类型 | URL（完整） | 抓取时间 (UTC) | 筛选算法 |
```

不得出现"今日热门 GitHub"这样无来源无口径的陈述。

### R4. 禁止引用未经查询的数据

常见幻觉类型：
- **stars 增速夸张**：某项目"36天破100K stars"——这类数字必须注明来源，且需二次验证
- **项目描述夸大**：README 自述的 benchmark 数字（如"96.6% R@5"）必须标注"来自 README 声明，未交叉验证"
- **skill 数量混淆**：某项目自称"72 design systems"，实际包含 design-skills 57 个，数字单位不同

当无法确认某个数字时，**必须明确标注"未确认"**，不得凭感觉填充。

## 三、Skill 升格判断（05-05 审计失败核心原因）

### R5. 深读项目必须有明确的 Skill 升格判断

格式如下：

```
## D. Skill 升格判断

**项目**：[owner/repo]

**判断**：[可直接迁移 / 需二次验证 / 暂不沉淀]

### 可直接迁移的部分：
1. [具体内容 + 为什么可直接迁移]

### 需要二次验证的部分：
1. [具体内容 + 需要什么验证]

### 暂不沉淀的部分：
1. [具体内容 + 为什么]
```

禁止：
- 完全没有 Skill 升格章节
- 只有"建议进一步研究"这样的空话，无具体判断

---

## 四、可复用动作

### R6. 每份报告必须有"可落地"章节

禁止只描述"这个项目是什么"，必须有"我们如何用"：
- 如果可迁移：说明需要哪些文件、修改哪些配置、影响哪些现有 workflow
- 如果暂不迁移：说明什么条件下才值得迁移

---

## 五、推送与交付

### R7. delivery 失败必须写入 runtime 并标注

当 delivery（推送）失败时：
1. 将报告完整内容写入 `shared/inbox/openclaw/daily/YYYY-MM-DD.md`
2. 在报告头部注明 `delivery_status: failed`
3. **不得**声称"已推送"或"发送成功"

### R8. 容器状态自检

开始学习前，检查 OpenClaw 容器状态。如果容器处于 Exited/Stopping 状态，先启动容器并等待 health: healthy 再执行学习。

## 六、报告完整性自检清单

在输出报告前，逐项核对：

- [ ] 抓取口径表完整（URL + 时间 + 筛选算法）
- [ ] 候选表七列齐全，stars 等数字来自实时 API
- [ ] 深读项目 C1~C6 六节完整，无截断
- [ ] Skill 升格判断有实质性三级分类
- [ ] 至少 3 条可复用动作或落地路径
- [ ] 标注了已知幻觉点和待验证项
- [ ] 无明文 secret
- [ ] delivery 失败时已写入 inbox 并标注

---

## 七、已知失败模式（快速对照）

| 失败模式 | 触发条件 | 应对方法 |
|---------|---------|---------|
| 报告截断 | 输出超长时模型自行截断 | 将深读拆成独立章节，每节不超过 200 行 |
| C3~C6 缺失 | 模型跳过中间章节 | 在 prompt 中明确要求 C1~C6 全部输出，缺一则重新生成 |
| Skill 升格缺失 | 模型忽略 D 节 | 将 Skill 升格判断作为独立步骤，放在 C 节之后、E 节（审计清单）之前 |
| delivery 假成功 | channel 未配置但模型声称"已发送" | 以 inbox 有无为唯一标准，inbox 无文件则视为失败 |
| 容器 Exited | 容器长期未运行 | 学习前加容器状态检查，Exited 时先 docker start |
