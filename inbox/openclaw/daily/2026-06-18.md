## 深读项目

### 1. vercel/eve

- **一句话判断**：Vercel 推出的文件系统优先 Agent 框架，将 agent 的 tools、skills、channels、schedules 全部映射为目录约定，适合需要可审计、可组合的生产级 agent 架构。
- **解决的问题**：当前 agent 框架（LangChain、CrewAI 等）多以代码 API 为中心，agent 配置散落在函数调用中，难以统一审查和运维。eve 将所有 agent 能力收敛为文件系统结构——`agent/instructions.md`、`agent/tools/*.ts`、`agent/skills/*.md`、`agent/channels/*.ts`、`agent/schedules/*.ts`——让 agent 成为一个可 `ls` 的项目。

- **架构/实现**：
  - 核心模块：`defineAgent`（配置）、`defineTool`（工具定义）、`defineSkill`（按需加载技能）、channels（Slack/Discord/Telegram/GitHub/Linear 等消息通道）、schedules（cron 任务）、sandbox（Docker/microsandbox/Vercel 沙箱执行）
  - 数据流：用户消息 → channel → agent runtime → model（Vercel AI SDK）→ tool calls → sandbox → response
  - 关键依赖：`ai`（Vercel AI SDK）、`zod`（schema 验证）、`nitro`（服务器运行时）、`next`/`react`/`vue`/`svelte`（前端集成）

- **repo tree 摘要**：
  ```
  vercel/eve (monorepo, pnpm workspaces + turbo)
  ├── packages/eve/           # 核心包，npm publish 的主体
  │   ├── src/
  │   │   ├── public/         # 对外 API：tools, skills, channels, hooks, sandbox, agents
  │   │   ├── shared/         # 内部共享类型定义
  │   │   ├── runtime/        # 运行时引擎：connections, agent loop
  │   │   ├── execution/      # 执行层：skills loader
  │   │   ├── setup/          # scaffold/init 脚手架
  │   │   ├── evals/          # eval 框架（loaders, reporters, expect）
  │   │   └── compiled/       # 编译产物缓存
  ```

- **⭐ 源码精读**：

  **1) `defineAgent` — Agent 配置定义函数**
  ```typescript
  // packages/eve/src/public/definitions/agent.ts
  export function defineAgent<TAgent extends AgentDefinition>(
    definition: ExactDefinition<TAgent, AgentDefinition>,
  ): TAgent {
    return definition;
  }
  ```
  纯透传函数，核心价值在 TypeScript 类型约束——编译期禁止未知字段，agent identity 从 `manifest.agentId`（包名/目录名）自动推导，无需手写 name。这是「文件系统即 identity」理念的代码体现。

  **2) `defineTool` 签名与 ToolContext — 工具定义核心**
  ```typescript
  // packages/eve/src/public/definitions/tool.ts (关键类型)
  export type ToolDefinition<TInput = unknown, TOutput = unknown> = PublicToolDefinition<TInput, TOutput> & {
    execute(input: TInput, ctx: ToolContext): Promise<TOutput> | TOutput;
    auth?: ToolAuthDefinition;
    needsApproval?: (ctx: NeedsApprovalContext<ApprovalToolInput<TInput>>) => boolean;
  };

  export type ToolContext = SessionContext & {
    getToken(): Promise<TokenResult>;
    requireAuth(): never;
  };
  ```
  工具自带 auth 和 approval 机制。`getToken()` 支持 OAuth interactive flow（框架自动暂停等待用户授权后重试），`needsApproval` 支持 always/never/once 等策略。这比大多数 agent 框架的 tool 定义丰富得多。

  **3) 内置工具工厂 — `defineBashTool`, `defineReadFileTool` 等**
  ```typescript
  // packages/eve/src/public/tools/index.ts (导出列表)
  export { type DefineBashToolInput, defineBashTool } from "#public/tools/define-bash-tool.js";
  export { type DefineGlobToolInput, defineGlobTool } from "#public/tools/define-glob-tool.js";
  export { type DefineGrepToolInput, defineGrepTool } from "#public/tools/define-grep-tool.js";
  export { type DefineReadFileToolInput, defineReadFileTool } from "#public/tools/define-read-file-tool.js";
  export { type DefineWriteFileToolInput, defineWriteFileTool } from "#public/tools/define-write-file-tool.js";
  ```
  提供标准化的文件操作工具集，每个都是可配置的工厂函数（通过 Input type 定制行为）。这意味着 eve agent 默认具备完整的文件系统操作能力。

- **依赖分析**：
  - 核心运行时依赖：`nitro`（服务器框架）、`ai`（Vercel AI SDK，peer dep）
  - 开发/可选依赖：`zod`（schema）、`next`/`react`/`vue`/`svelte`（前端框架集成）、`@ai-sdk/anthropic`、`@ai-sdk/openai`、`@ai-sdk/google`（模型 provider）、`@vercel/sandbox`、`microsandbox`、`just-bash`（沙箱）、`turndown`（HTML→Markdown）
  - 供应链风险：依赖链较深（Vercel 生态内部包多），但均为 Vercel 官方维护；Node >= 24 要求较高，可能限制生产环境部署

- **可复用经验**：
  - 当设计 agent 框架时，应优先采用「文件系统即配置」模式——将 tools、skills、instructions 映射为目录约定，让 agent 结构可 `ls`、可 diff、可 code review
  - 当需要 tool 审批机制时，应优先参考 eve 的 `needsApproval` + `getToken`/`requireAuth` 模式，支持 per-tool 粒度的授权策略

- **可尝试实验**：
  ```bash

  # 编辑 agent/instructions.md 写入系统提示

  npm run dev  # 启动交互式终端 UI
  ```

- **风险边界**：
  - License: Apache-2.0，商用友好
  - Beta 阶段（subject to Vercel beta terms），API 可能变更
  - Node >= 24 要求激进，生产环境兼容性需验证
  - 与 Vercel 生态深度绑定（sandbox、deploy、connect），非 Vercel 用户需评估迁移成本

- **⭐ Skill 升格判断**：**需二次验证** — eve 的文件系统约定（tools/、skills/、channels/、schedules/）与 Hermes/OpenClaw 的 skill 目录结构有天然亲和性，但 eve 是完整 runtime 框架而非独立 skill，需要验证其核心理念能否提取为 Hermes skill 模板。

- **⭐ 落地路径**：
  1. 提取 eve 的目录约定模式，在 OpenClaw 中定义标准化 agent 项目模板（`agent/instructions.md` + `agent/tools/` + `agent/skills/`）

### 2. tamnd/kage

- **一句话判断**：Go 语言实现的网站离线镜像工具，用真实 headless Chrome 渲染页面后剥离全部 JavaScript，产出纯静态 HTML+CSS+图片，支持打包为 ZIM 归档或自包含可执行文件。
- **解决的问题**：浏览器「另存为」保存的网页依赖外部 JS，离线打开时白屏、加载动画不停、追踪脚本仍在运行。kage 的方案是：先用真实浏览器完成渲染，抓取最终 DOM 快照，然后彻底删除所有脚本——得到的是「照片」而非「程序」。

- **架构/实现**：
  - 数据流：`seed URL → headless Chrome 渲染 → 最终 DOM 快照 → strip JS（sanitize）→ 本地化资源（asset）→ 写入磁盘`
  - 核心模块：`clone/`（爬虫引擎：frontier、render workers、asset workers、resume state）、`browser/`（Chrome 控制和 DOM 快照）、`sanitize/`（JS 剥离）、`asset/`（CSS/图片/字体下载和本地化）、`urlx/`（URL→文件路径确定性映射）、`zim/`（纯 Go ZIM 读写器）、`pack/`（打包为 ZIM/可执行文件/AppImage）、`viewer/`（离线展示：浏览器或 native window）
  - 关键依赖：`go-rod`（headless Chrome 控制）、`cobra`（CLI）、`lipgloss`（TUI 美化）、`webview`（native window）、`klauspost/compress`（zstd 压缩）

- **repo tree 摘要**：
  ```
  tamnd/kage
  ├── cmd/kage/        # 薄入口：固定主线程后交给 cli.Execute
  ├── cli/             # cobra 命令树和 flag 绑定
  ├── clone/           # 爬虫引擎：frontier、渲染 worker、资源 worker、断点续爬
  ├── browser/         # headless Chrome 控制和 DOM 快照
  ├── sanitize/        # JS 剥离：script、event handler、javascript: URL
  ├── asset/           # CSS/图片/字体下载和路径本地化
  ├── urlx/            # 确定性 URL→文件路径映射（纯函数，无副作用）
  ├── zim/             # 纯 Go ZIM 格式读写器
  ├── pack/            # 镜像→ZIM/自包含二进制/AppImage 打包
  ├── viewer/          # 离线展示：系统浏览器或 native window (webview)
  └── docs/            # tago 文档站
  ```

- **关键源码文件**：
  | 路径 | 用途 | 关键内容 |
  |------|------|----------|
  | `sanitize/sanitize.go` | JS 剥离核心 | `Strip()` / `CleanTree()` 函数，递归遍历 DOM 删除 script、on* handler、javascript: URL、IE conditional comment、dead link hint |
  | `urlx/urlx.go` | URL 标准化与路径映射 | `ParseSeed()`、`Normalize()`、`LocalPath()`、`Rel()` 纯函数；Page/Asset 分类；binaryExts 表 |
  | `go.mod` | 依赖清单 | Go 1.26.4，核心：go-rod、cobra、lipgloss、webview、zstd |

- **⭐ 源码精读**：

  **1) `sanitize.Strip()` — 一站式 JS 剥离**
  ```go
  // sanitize/sanitize.go
  func Strip(doc []byte, opts Options) ([]byte, Report, error) {
      root, err := html.Parse(bytes.NewReader(doc))
      if err != nil {
          return nil, Report{}, err
      }
      rep := CleanTree(root, opts)
      var buf bytes.Buffer
      if err := html.Render(&buf, root); err != nil {
          return nil, rep, err
      }
      return buf.Bytes(), rep, nil
  }
  ```
  解析 HTML → 清洗 DOM 树 → 重新渲染。返回 `Report` 统计删除了多少 script、handler、JS URL、conditional comment，便于用户评估清洗效果。

  **2) `sanitize.clean()` — 递归 DOM 清洗核心**
  ```go
  // sanitize/sanitize.go
  func clean(n *html.Node, opts Options, rep *Report) {
      var next *html.Node
      for c := n.FirstChild; c != nil; c = next {
          next = c.NextSibling
          if c.Type == html.CommentNode {
              if isConditionalComment(c.Data) {
                  n.RemoveChild(c)
                  rep.CondCommentsRemoved++
              }
              continue
          }
          if c.Type == html.ElementNode {
              switch c.DataAtom {
              case atom.Script:
                  n.RemoveChild(c); rep.ScriptsRemoved++; continue
              case atom.Noscript:
                  if opts.KeepNoscript { unwrapNoscript(n, c); rep.NoscriptUnwrapped++ }
                  else { n.RemoveChild(c); rep.NoscriptRemoved++ }; continue
              case atom.Link:
                  if isDeadLink(c) { n.RemoveChild(c); rep.DeadLinksRemoved++; continue }
              }
              stripHandlers(c, rep)
              neutralizeJSURLs(c, rep)
          }
          clean(c, opts, rep)
      }
  }
  ```
  处理 7 种清洗场景：`<script>`、`<noscript>`、IE conditional comment、on* 事件属性、javascript: URL、dead link hint（preconnect/dns-prefetch/modulepreload）、meta-refresh。注意 `next = c.NextSibling` 的提前保存——删除节点后仍能正确遍历。

  **3) `urlx.Normalize()` — URL 标准化与过滤**
  ```go
  // urlx/urlx.go
  func Normalize(base *url.URL, ref string) (*url.URL, error) {
      ref = strings.TrimSpace(ref)
      if ref == "" { return nil, fmt.Errorf("empty reference") }
      if strings.HasPrefix(ref, "#") { return nil, fmt.Errorf("fragment-only reference") }
      low := strings.ToLower(ref)
      for _, bad := range []string{"javascript:", "mailto:", "tel:", "data:", "blob:", "about:", "ftp:", "sms:"} {
          if strings.HasPrefix(low, bad) { return nil, fmt.Errorf("non-crawlable scheme: %s", bad) }
      }
      r, err := url.Parse(ref)
      if err != nil { return nil, fmt.Errorf("parse ref %q: %w", ref, err) }
      var abs *url.URL
      if base != nil { abs = base.ResolveReference(r) } else { abs = r }
      if abs.Scheme != "http" && abs.Scheme != "https" { return nil, fmt.Errorf("non-http scheme: %q", abs.Scheme) }
      if abs.Host == "" { return nil, fmt.Errorf("reference has no host") }
      return canonical(abs, false), nil
  }
  ```
  过滤 8 种不可爬取的 scheme，解析相对 URL，标准化 scheme/host 大小写，去掉 fragment 和默认端口。这是 kage 确定性映射的基础——两个「看起来不同」的 URL 在这里归一化为同一个 key。

- **依赖分析**：
  - 核心：`go-rod`（Chrome DevTools Protocol Go 客户端）、`cobra`（CLI 框架）、`golang.org/x/net/html`（HTML 解析）、`klauspost/compress`（zstd 压缩）
  - 可选：`webview/webview_go`（native window，需 cgo）、`lipgloss`（TUI 美化）
  - 供应链风险：go-rod 依赖链较浅，整体依赖量可控；Go 模块生态供应链风险较低

- **可复用经验**：
  - 当需要网页归档时，应优先采用「先渲染后清洗」模式（headless Chrome 渲染 → DOM 快照 → JS 剥离），而非简单抓取 HTML 源码——SPA 站点的源码不含实际内容
  - 当设计 URL→文件路径映射时，应优先参考 kage 的 `urlx` 包——纯函数、确定性、无副作用，使得 link rewrite 可以在 asset 下载前完成

- **可尝试实验**：

- **风险边界**：
  - License: MIT，完全自由使用

  - 大型网站爬取耗时较长（受限于 headless Chrome 渲染速度）

- **⭐ 落地路径**：

### 3. mrtooher/fable-mode

- **一句话判断**：Claude skill，通过结构化 stage map + failable verification check + self-critique 三步约束 LLM 在复杂任务中的执行纪律，三个变体（inline/sonnet/haiku）适配不同成本场景。
- **解决的问题**：LLM 在多文件、多步骤、多 session 的复杂任务中容易「一步错、步步错」——早期假设错误到后期才发现，或「看起来对」但未实际验证。fable-mode 不改变模型能力上限，而是用程序化纪律约束执行过程：先计划再动手、每步必须有可失败的检查、交付前自我审查。

- **架构/实现**：
  - 核心循环（4 步）：① Stage Map（写阶段计划）→ ② Delegate（如支持 subagent 则并行委派）→ ③ Verify with failable check（每步必须有能失败的验证）→ ④ Self-critique（交付前怀疑性自审）
  - 三个变体：`fable-mode`（inline，当前模型）、`fable-sonnet`（spawn Sonnet subagent）、`fable-haiku`（spawn Haiku subagent）
  - 领域特定模式：Software Engineering（测试为 failable check）、Research（源追溯为 check）、Data Analysis（数据质量断言为 check）、Long-running（done criteria 为 check）
  - 运营规则：warning threshold（累计 3 个警告必须停下来汇报）、find-and-replace safety（sed 替换必须用 word boundary）

- **repo tree 摘要**：

- **⭐ 源码精读**：

  **1) SKILL.md frontmatter — 触发条件定义**
  ```yaml
  ---
  name: fable-mode
  description: >
    Enforces staged execution discipline on large tasks: a written stage plan,
    parallel delegation where the runtime supports it, a failable verification
    check at each stage, and a skeptical self-review before delivery. Trigger
    when the user explicitly asks ("do this thoroughly", "be systematic",
    "deep work mode") OR when the task objectively spans multiple
    files, multiple sources, or multiple sessions. Do NOT trigger on ordinary
    multi-step requests that a direct attempt handles fine.
  ---
  ```
  触发条件是关键设计：用户显式请求「be systematic」**或** 任务客观上跨越多文件/多源/多 session。不触发于普通多步请求。这是避免「仪式化」过度 staging 的阀门。

  **2) 核心循环 Step 3 — Failable Check 的定义**
  ```markdown
  Each stage must define a pass condition that an external artifact satisfies.
  Acceptable checks:
  - a test that runs and passes
  - a file or output that provably exists in the expected shape
  - a source actually fetched and read, not assumed
  - an output diffed against the stated spec

  "I reviewed it and it looks right" is not a check.
  ```
  这是整个 skill 最核心的设计决策：将「验证」从主观感受（looks right）提升为客观可失败的外部检查。如果一个阶段没有可失败的检查，必须显式标记为 unverified。

  **3) EXAMPLE.md — 一个 failable check 捕获 bug 的实例**
  ```javascript
  // One-shot 版本（看起来正确但有 bug）：
  export async function GET(req) {
    const user = await getUser(req);
    const count = await db.calls.count({
      where: { userId: user.id, createdAt: { gte: startOfMonth() } }
    });
    return Response.json({ count });
  }

  // Fable-mode 阶段 3 的测试（能失败的检查）：
  test('unauthenticated request returns 401', async () => {
    const res = await GET(mockReq({ session: null }));
    expect(res.status).toBe(401);   // FAILS — 原版返回 500
  });

  // 修复后：
  const user = await getUser(req);
  if (!user) return new Response('Unauthorized', { status: 401 });
  ```
  一个测试就捕获了「happy path 看起来对但 error path 有 bug」的经典问题。这就是「check that can fail」vs「I reviewed it and it looks right」的本质区别。

## 经验沉淀

1. **当设计 agent 框架的 tool/skill 定义时，应优先采用「文件系统即配置」模式** — eve 将 tools/、skills/、channels/、schedules/ 映射为目录约定，让 agent 结构可 ls、可 diff、可 review。这比代码内散落的 API 调用更容易审计和运维。

2. **当需要安全地归档网页内容时，应优先采用「先渲染后清洗」而非简单抓取源码** — kage 用 headless Chrome 渲染最终 DOM 后剥离全部 JS，产出的是「照片」而非「程序」。SPA 站点的源码不含实际内容，必须先渲染。

3. **当 LLM 执行复杂多步任务时，应优先强制每步定义一个「能失败的检查」** — fable-mode 的核心洞察是：「I reviewed it and it looks right」不是验证，一个能运行并失败的测试才是验证。错误在 stage 3 捕获的成本远低于 stage 8。

4. **当需要 URL→文件路径映射时，应优先设计为纯函数、确定性、无副作用的归一化层** — kage 的 urlx 包在 asset 下载前就能确定其最终路径，使得 link rewrite 可以与下载并行。这种「先确定路径、后填充内容」的模式适用于任何需要缓存或归档的场景。
