## 深读项目

### 🔬 深读 1：microsoft/SkillOpt

**一句话判断**：把"训练 LLM"的整套深度学习 vocabulary（epoch / batch / LR scheduler / gradient clip / held-out validation）原封不动搬到"训练 prompt / skill 文档"上，是 2026 年最有代表性的"agent 自我进化"范式之一。

#### 解决的问题

传统 agent skill 是"手写 / 一次性 LLM 生成 / 模糊自我修订"，三种都没有可重复的改进路径。SkillOpt 把 skill 当作 frozen agent 的"可训练 state"，用 held-out 验证门控 + bounded edit 让改进可观测、可回滚、可跨模型迁移。

**① `scheduler.py` —— 把"DL 的 LR scheduler" 1:1 翻译到"每步允许的 skill edit 数"**

```python
class LRScheduler(ABC):
    """Base class for edit-budget schedulers."""
    def __init__(self, max_lr: int, min_lr: int, total_steps: int) -> None:
        self.max_lr = max_lr
        self.min_lr = min_lr
        self.total_steps = total_steps
        self._current_step = 0

    @abstractmethod
    def _compute_lr(self, step: int) -> int:
        """Return the edit budget for the given 1-indexed step."""

    def step(self) -> int:
        self._current_step += 1
        return self._compute_lr(self._current_step)

class CosineScheduler(LRScheduler):
    def _compute_lr(self, step: int) -> int:
        if self.total_steps <= 1:
            return self.max_lr
        t = min(step, self.total_steps) / self.total_steps
        lr = self.min_lr + 0.5 * (self.max_lr - self.min_lr) * (1 + math.cos(math.pi * t))
        return max(self.min_lr, round(lr))

class AutonomousScheduler(LRScheduler):
    """No edit limit — the model decides freely."""
    NO_LIMIT = 999
    def _compute_lr(self, step: int) -> int:
        return self.NO_LIMIT
```

#### 可复用经验（≥3 条）

1. 当**想让 agent 的 prompt/skill 在冻结模型上稳定变好**时，应优先把"训练循环"显式建模为 epoch / batch / LR / held-out gate，因为手改 prompt 没有可观测改进路径。
2. 当**改写预算需要动态调节**时（Hermes 每天 candidate facts 可能爆量），应优先用"调度器 + 重要度排序"两步组合（先定预算、再 ranking），而非一次性 prompt 让 LLM 决定。
3. 当**让 LLM 做"自我评估"** 时，应优先用 held-out 集合 + 严格提升门槛，否则 LLM 会用"主观感觉"批准自己的修改，导致悄悄漂移。
4. （bonus）当**让 LLM 修改自己的配置文件** 时，应优先把"optimizer"与"target"解耦为两个角色（不同 model / 不同 prompt），参考 `meta_skill` 的设计。

#### 可尝试实验（30 分钟内）

- 写一个 `mini_skillopt.py`：把 Hermes 当前 SOUL.md 当 skill，构造一个 5-task 的 held-out 测试集（用户偏好问答 ×5），跑 3 epoch 的 constant LR=2 edit + cosine LR=2→0.5 decay，对比初始 vs 优化后 skill 的 task pass rate。
- 完整不需要任何 API key——把 optimizer 换成 "string.replace rules" 也能 demo 流程。

#### 风险边界

- **License**：MIT（兼容）。可复用代码片段。
- **维护活跃度**：高，v0.1.0 在 PyPI（2026-06-02），v0.2.x 在路上，SkillOpt-Sleep 在 2026-06-08 发布。
- **安全风险**：所有 API key 走 `AZURE_OPENAI_API_KEY` / `ANTHROPIC_API_KEY` / `MINIMAX_API_KEY` env vars；Hermes/OpenClaw 复用时要走 `shared-memory-bridge` 的占位符。
- **不适用场景**：任务数量极少（<3）时无 held-out；纯创意写作（没有客观评分标准）时门控失效。
- **供应链**：可选依赖含 vllm/gradio，体量较大；正式部署建议只装核心。

### 🔬 深读 3：alibaba/open-code-review

**一句话判断**：把"通用 agent 在大 changeset 上做 code review"失败的根因归结为"缺少硬约束"，并用 Go 写了一套 deterministic×agent hybrid 的硬约束流水线——是 2026 年大厂开源里少见的"工程哲学 + 可运行代码"同时成立的范例。

#### 解决的问题

通用 agent 做 code review 三大痛点：incomplete coverage / position drift / unstable quality。根因是"纯语言驱动缺乏硬约束"。open-code-review 的解法是：

- **文件选择**：确定哪些文件 review、哪些过滤，不能让 agent 偷懒
- **Smart bundling**：相关文件 bundle 在一起，独立 sub-agent 并发
- **Fine-grained rule matching**：规则与文件特征匹配，不是 prompt 里说"如果有 X 请注意"
- **External positioning + reflection**：comment 位置不对时独立模块纠错
- **Agent 留在动态决策**：prompt 模板 + toolset

**① `agent.go` CommentWorkerPool —— 后台 goroutine 池处理评论后处理**

```go
type CommentWorkerPool struct {
    semaphore chan struct{}
    wg        sync.WaitGroup
    resultsMu sync.Mutex
    results   []model.LlmComment
}

func NewCommentWorkerPool(workerCount int) *CommentWorkerPool {
    if workerCount <= 0 { workerCount = 8 }
    return &CommentWorkerPool{semaphore: make(chan struct{}, workerCount)}
}

func (p *CommentWorkerPool) Submit(f func() ([]model.LlmComment, error)) {
    p.wg.Add(1)
    go func() {
        defer p.wg.Done()
        p.semaphore <- struct{}{}
        defer func() { <-p.semaphore }()
        comments, err := f()
        if err != nil { fmt.Fprintf(stdout.Writer(), "[ocr] CommentWorkerPool error: %v\n", err) }
        p.resultsMu.Lock()
        p.results = append(p.results, comments...)
        p.resultsMu.Unlock()
    }()
}
```

**② `agent.go` dispatchSubtasks —— semaphore + wg + ctx-timeout 并发模板**

```go
func (a *Agent) dispatchSubtasks(ctx context.Context) ([]model.LlmComment, error) {
    a.diffs = a.filterLargeDiffs(a.diffs)
    if len(a.diffs) == 0 { return nil, fmt.Errorf("all diffs filtered out by token size") }

    var wg sync.WaitGroup
    concurrency := a.args.MaxConcurrency
    if concurrency <= 0 { concurrency = 8 }
    sem := make(chan struct{}, concurrency)
    timeout := time.Duration(a.args.ConcurrentTaskTimeout) * time.Minute

    var dispatched int64
    for i := range a.diffs {
        if a.diffs[i].IsDeleted { continue }
        dispatched++
        wg.Add(1)
        sem <- struct{}{} // acquire
        go func(d model.Diff) {
            defer wg.Done()
            defer func() { <-sem }() // release
            fileCtx := ctx
            if timeout > 0 {
                var cancel context.CancelFunc
                fileCtx, cancel = context.WithTimeout(ctx, timeout)
                defer cancel()
            }
            if err := a.executeSubtask(fileCtx, d); err != nil {
                atomic.AddInt64(&a.subtaskFailed, 1)
                a.recordWarning("subtask_error", d.NewPath, err.Error())
            }
        }(a.diffs[i])
    }
    wg.Wait()
    // ... collect from CommentWorkerPool ...
}
```

## 经验沉淀（通用经验）

> 三条结构化经验，下方"候选反哺"再细化。

1. **当 LLM 需要修改"自己的行为文件"（skill / memory / review 模板）时，应优先把"训练循环"显式建模为 epoch / LR scheduler / held-out validation gate / bounded edit，而不是直接让 LLM 重写。** 因为缺乏硬约束的"自我修订"会产生不可观测的漂移。SkillOpt 的整套 vocabulary 提供了可直接复用的工程模板。

2. **当需要把 LLM 嵌入批处理流水线时，应优先采用 "deterministic 过滤 → per-unit sub-agent 并发 → 独立 reflection 模块"三段架构**，而不是把"判断/筛选/重试"全塞进一个 prompt。open-code-review 的 Preview → dispatchSubtasks → ReLocateComment 是范本；claude-mem 的 3-layer search/timeline/get_observations 是检索侧的对应范本。

3. **当为多 agent host / 多 IDE 写插件时，应优先把"manifest + lifecycle hooks + 独立 worker 进程"分层**。claude-mem 的 plugin/ + src/services 拆法 + SkillOpt-Sleep 的 plugin/ 子目录 + `decoupled from paper code` 注释，都是"主代码不动、外围壳子独立升级"的实践。这种分层也避免了污染主 agent 的 system prompt。

4. **当需要让 agent "夜间自我进化"时，应优先走 offline replay + held-out gate + 人工采纳模式（参考 SkillOpt-Sleep 的 Sleep cycle），而不是让 agent 在主 session 内边做任务边改自己**。skillopt_sleep 包与 skillopt 包的解耦是这个边界最清晰的表达。

5. **当供应链审计时，应优先剔除"看起来无害但会外发数据"的依赖**（posthog-node / bullmq 全套 / tree-sitter 全家桶）。依赖少即审计面小——open-code-review 的 6 个 direct require 比 claude-mem 的 24 个 dependencies 更值得参照。
