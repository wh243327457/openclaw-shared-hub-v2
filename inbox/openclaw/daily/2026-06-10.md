### 可复用经验（项目级）

> 当 portable skill 同时支持 50+ harness 时，应优先用「**SKILL.md 入口契约 + STEP 0 stale-clone 检查 + MANDATORY first-line badge + 元数据 metadata.openclaw**」四件套，而不是写 50 套适配器，因为：
> - **SKILL.md** 是唯一入口；harness 用 `Read` 加载，不依赖任何平台专有 API
> - **STEP 0** 防御 harness cache 比 git origin 慢的 bug（Claude Code marketplace 已知问题）
> - **MANDATORY badge** 强制模型先读 SKILL.md 再回答，避免 improvisation 飘移
> - **metadata.openclaw.optionalEnv** 把"按需装配"写到元数据，runtime 按 env 决定能力
>
> 边界是 skill 必须有可写方法论契约；纯工具型 skill 不适用。

> 当 skill 需要跨多源异构 walled garden 时，应优先用「**LLM planner 生成 subqueries + ThreadPoolExecutor 并发 fetch + weighted_rrf 融合 + Phase 2 实体抽取反向搜索 + thin source retry**」五阶段 pipeline，而不是串行调用各源 API，因为：
> - planner 把"搜什么"和"在哪搜"分离，便于 per-source cap
> - 并发 + 429 sharing 让单源 rate limit 不拖垮整次 run
> - weighted_rrf 允许给"主 handle"和"related handle"不同权重
> - Phase 2 反向搜索把"实体人名"接回 Phase 1 的 source
>
> 边界是必须有 LLM planner；纯 deterministic 检索不适用。

> 当 skill 需要可审计的质量门禁时，应优先把「**verify_unit / verify_diagnose / verify_smoke / verify_latency / verify_eval**」五阶段写死为 subprocess 编排脚本，而不是依赖手动测试，因为：
> - 升级后自动回归，跑过没看 JSON 一眼明白
> - baseline=HEAD~1 / candidate=WORKTREE 是 Git 自带的 A/B 测试基础设施
> - median of 5 runs 抵消单次抖动
>
> 边界是必须有 head/tail git 历史；纯一次性 skill 不适用。

**1. `turbovec/src/lib.rs` — `TurboQuantIndex::add` 核心逻辑**

```rust
pub fn add(&mut self, vectors: &[f32]) {
    let dim = self.dim.expect("use add_2d(vectors, dim) on first add");
    let n = vectors.len() / dim;
    if n == 0 { return; }  // ← 空 first add 不再 lock TQ+ identity calibration
    if let Some((vi, ci, v)) = first_invalid_coord(vectors, dim) {
        panic!("invalid input value at vector {vi}, coord {ci}: {v}");
    }
    let rotation = self.rotation.get_or_init(|| rotation::make_rotation_matrix(dim));
    if self.boundaries.get().is_none() || self.centroids.get().is_none() {
        let (b, c) = codebook::codebook(self.bit_width, dim);
        let _ = self.boundaries.set(b);
        let _ = self.centroids.set(c);
    }
    let existing = if self.tqplus_shift.is_empty() { None }
                   else { Some((&self.tqplus_shift, &self.tqplus_scale)) };
    let (packed, scales, shift, scale_tq) = encode::encode(
        vectors, n, dim, rotation, boundaries, centroids,
        self.bit_width, existing,
    );
    if self.n_vectors == 0 {
        self.packed_codes = packed; self.scales = scales;
        self.tqplus_shift = shift; self.tqplus_scale = scale_tq;  // ← 冻结 calibration
    } else {
        self.packed_codes.extend_from_slice(&packed);
        self.scales.extend_from_slice(&scales);
        // tqplus_shift/scale unchanged — locked by first add
    }
    self.n_vectors += n;
    self.blocked = OnceLock::new();  // ← invalidate cache
}
```

**2. `turbovec/src/lib.rs` — `search_with_mask` 过滤 inside-SIMD**

```rust
pub fn search_with_mask(&self, queries: &[f32], k: usize, mask: Option<&[bool]>) -> SearchResults {
    let nq = queries.len() / dim;
    let rotation = self.rotation.get_or_init(|| rotation::make_rotation_matrix(dim));
    let centroids = self.centroids.get_or_init(|| { let (_, c) = codebook::codebook(self.bit_width, dim); c });
    let blocked = self.blocked.get_or_init(|| { 
        let (data, n_blocks) = pack::repack(&self.packed_codes, self.n_vectors, self.bit_width, dim);
        BlockedCache { data, n_blocks }
    });
    let packed_mask = mask.map(|m| {
        let n_words = (self.n_vectors + 63) / 64;
        let mut buf = vec![0u64; n_words];
        for (i, &b) in m.iter().enumerate() { if b { buf[i >> 6] |= 1u64 << (i & 63); } }
        buf
    });
    let n_allowed = packed_mask.as_ref().map_or(self.n_vectors, |p| p.iter().map(|w| w.count_ones() as usize).sum());
    let effective_k = k.min(self.n_vectors).min(n_allowed);
    let (scores, indices) = search::search(queries, nq, rotation, &blocked.data, centroids, 
                                            &self.scales, &self.tqplus_shift, &self.tqplus_scale,
                                            self.bit_width, dim, self.n_vectors, blocked.n_blocks, k,
                                            packed_mask.as_deref());
    SearchResults { scores, indices, nq, k: effective_k }
}
```

```rust
    -> PyResult<(Bound<'py, PyArray2<f32>>, Bound<'py, PyArray2<i64>>)> {
    let arr = queries.as_array();
    let nq = arr.nrows();
    let q_slice = arr.as_slice().ok_or_else(|| not_contiguous_err("queries"))?;
    // 显式 typed error 而不是 Rust panic
    if let Some(idx_dim) = self.inner.dim_opt() {
        if arr.ncols() != idx_dim {
            return Err(pyo3::exceptions::PyValueError::new_err(format!(
                "query dim {} does not match index dim {}", arr.ncols(), idx_dim,
            )));
        }
    }
    // ... allowlist / mask 处理同上 ...
    let results = self.inner.search_with_mask(q_slice, k, mask_slice);
    let scores = numpy::ndarray::Array2::from_shape_vec((nq, results.k), results.scores)?
        .into_pyarray(py);
    let indices = numpy::ndarray::Array2::from_shape_vec((nq, results.k), results.indices)?
        .into_pyarray(py);
    Ok((scores, indices))
}
```

**4. `lib.rs` — `first_invalid_coord` NaN/Inf/Huge-magnitude 显式校验**

```rust
const MAX_INPUT_MAGNITUDE: f32 = 1e16;
fn first_invalid_coord(values: &[f32], dim: usize) -> Option<(usize, usize, f32)> {
    for (i, x) in values.iter().enumerate() {
        if !x.is_finite() || x.abs() >= MAX_INPUT_MAGNITUDE {
            let vector_index = if dim == 0 { 0 } else { i / dim };
            let coord_index = if dim == 0 { i } else { i % dim };
            return Some((vector_index, coord_index, *x));
        }
    }
    None
}
```

### 可复用经验（项目级）

> 当向量索引需要流式摄入且不允许训练阶段时，应优先用「**数据无关量化器（random rotation + Beta 分布 + Lloyd-Max from math, not from data）+ TQ+ per-coord calibration 冻结**」双层架构，而不是 IVFFlat / HNSW 等训练驱动索引，因为：
> - 数据无关 = 第一个 add 就用上，无需冷启动
> - TQ+ calibration 在 first add 拟合 shift/scale per-coord 冻结 → 后续 add 复用 → recall 不漂移
> - 16× 压缩（FP32 → 4-bit）让 10M 向量从 31 GB → 4 GB
>
> 边界是必须接受 ≤4-bit 精度；需要 8-bit 以上精度不适用。

> 当 vector search 需要 selective filter 时，应优先把 allowlist 预 pack 成 u64 bitmask 传进 SIMD kernel，而不是先全量搜再 filter，因为：
> - 32-vector block 粒度短路：blocks with no allowed 直接跳过
> - 节省 90% SIMD 工作（selective 场景下）
> - `effective_k = min(k, len(allowed))` 而不是 padded fallback
>
> 边界是 allowlist 至少要能 pack 成位掩码（uint64）。

> 当 Rust API 需要 lock-free 高 QPS read + mutation 时，应优先用「**4 个 OnceLock<Vec<T>> 缓存 + add 时直接 `self.blocked = OnceLock::new()` 替换**」而不是 Arc<RwLock<>>, 因为：
> - search(&self) 不用锁，第一次 caller 付 init 成本，后续 caller lock-free read
> - add(&mut self) 已经独占写权限，OnceLock 替换是 O(1)
> - 比 Mutex 跨线程读性能高一档
>
> 边界是初始化必须确定性（不能依赖运行时数据），否则不能 OnceLock 缓存。

> 当 embedding 来自不可信输入（用户上传 / 第三方 API）时，应优先在 `add()` 显式 panic NaN/Inf/Huge-magnitude 而不是 silent corruption，因为：
> - `0 * NaN = NaN` 会毒化整个 SIMD batch
> - `MAX_INPUT_MAGNITUDE = 1e16` 防 f32 sum-of-squares overflow to Inf
> - `add_2d()` 返回 typed `AddError::InvalidInputValue` 让 Python 端能 `try/except`
>
> 边界是 trusted 内部分支可以省（性能）；不可信 ingest 必须加。

```markdown
## Design Principles

### Filesystem as the single source of truth
The vault is a folder of plain markdown files. The app never owns the data — it only
reads and writes files. The cache, React state, and any in-memory representation are
always derived from the filesystem and must be reconstructible by deleting them.

### Three representations, one authority
1. **Filesystem** — the `.md` files on disk (source of truth)
2. **Cache** — `~/.laputa/cache/<hash>.json` (fast startup index, reconstructible)
3. **React state** — `VaultEntry[]` during a session (derived from cache or FS)

#### Invariants
1. **Disk-first writes**: All functions that change vault data must write to disk 
   (via Tauri IPC) *before* updating React state.
2. **Optimistic UI with rollback**: State may update before disk confirmation — 
   but failure callback must revert.
3. **No orphan state updates**: Never `updateEntry()` before `handleUpdateFrontmatter()` resolves.
4. **Recovery via reload**: `reload_vault` command deletes cache + rescans FS.
5. **Cache is disposable**: `reload_vault` deletes cache before rescan.
6. **Visibility filters are command-boundary concerns**: Gitignored-content visibility 
   applied after scanning, before React consumes entries.

| Layer | Owner | Writes to | Reads from |
|-------|-------|-----------|------------|
| Filesystem | Tauri Rust commands | Disk | — |
| Cache | `scan_vault_cached()` in `vault/cache.rs` | `~/.laputa/cache/` | FS + git diff |
| React state | `useVaultLoader` + actions | In-memory | Cache / FS |
```

### 可复用经验（项目级 — 深读项目3：refactoringhq/tolaria）

> 当 vault-style app 需要崩溃一致性时，应优先用「**Filesystem as SoT + Cache 层（可删）+ Disk-first invariant + Identity-matched cache reuse (modifiedAt + fileSize)**」四件套，而不是把 state 全放 SQLite 或 IndexedDB，因为：
> - 用户期待「这个 app 关了/崩了数据还在」
> - Cache layer (`~/.laputa/cache/<hash>.json`) 只为启动加速，可删
> - Identity-matched cache（`byte_len + content_hash`）比单纯 mtime 更可靠
> - Disk-first invariant 保证 React state 不领先 disk（崩溃可恢复）
>
> 边界是写入吞吐受 disk IO 限制；纯实时协作场景不适用（需要 CRDT）。

> 当 vault 想给 AI agent 提供专用 tools 而不只是通用 fs 时，应优先用「**内嵌 MCP server (stdio) + WebSocket UI bridge**」而不是 fork 一个 MCP 标准 server，因为：
> - MCP stdio 让 AI agent 用统一协议调用 vault-specific tools（search_notes / get_note / create_note）
> - WS UI bridge 让 MCP 工具可以反过来操作 UI（highlight_editor / open_note）
> - `requestedVaultPath()` 校验 active vault 防越权
> - tool annotations 区分 read-only / create / destructive
>
> 边界是必须支持 stdio transport 的 AI agent；纯 GUI-only app 不适用。

> 当 frontmatter 是 AI 读取契约时，应优先用「**约定 > 配置的 8 个标准字段名（type/status/url/Workspace/belongs_to/related_to/has/start_date/end_date）+ override 走 vault-level config 文件**」而不是让用户自由定义，因为：
> - 约定让 AI agent 不用先读 config 就能理解 vault 结构
> - `_pinned_properties` / `_icon` / `_width` 用 underscore 前缀标记 system-managed
> - 配置覆盖只在 `config/relations.md` 等显式文件，降低 AI 误读概率
>
> 边界是用户群必须是「想用 AI 读 vault」的；纯人工编辑用户不需要。

> 当一个 app 同时存在「vault 数据」和「机器偏好」两类信息时，应优先用「**vault 走 frontmatter（_field 系统字段）+ app 走 `~/.config/com.<org>.app/settings.json` + localStorage**」三处分层，而不是混在一起，因为：
> - 用户期待 vault 数据跨设备一致；机器偏好不应该跨设备
> - 例如 `_pinned_properties` 在 type note frontmatter，editor zoom 在 app settings
>
> 边界是单机 app 不适用（单设备没「跨设备」问题）；multi-device sync 必备。

> 当 vault watcher 需要响应外部修改（git pull / 其他 app）时，应优先用「**Rust notify crate watcher → 'vault-changed' events → React batched useVaultWatcher + token-based stale guard**」而不是 React 内 setInterval 轮询 FS，因为：
> - notify crate 是 native 事件，不浪费 CPU
> - token-based stale guard（generation/source-content）防 stale parse 覆盖新内容
> - 同 app owned save 通过 modifiedAt + fileSize 自识别，不触发重复 refresh
>
> 边界是网络盘（NFS / SMB）下 notify 事件可靠性下降；本地 FS 必备。

## 经验沉淀（5 条通用经验）

### 78. Portable skill 同时支持 50+ harness 时，应优先用「SKILL.md 入口 + STEP 0 stale-check + MANDATORY badge + metadata.openclaw」四件套

**经验**: 当 portable skill 同时支持 50+ harness（Claude Code / Codex / Cursor / OpenCode / Hermes / claude.ai web）时，应优先用「SKILL.md 入口契约 + STEP 0 stale-clone 检查 + MANDATORY first-line badge + metadata.openclaw optionalEnv」四件套，而不是写 50 套适配器，因为：
- SKILL.md 是唯一入口；harness 用 Read 加载，不依赖任何平台专有 API
- STEP 0 防御 harness cache 比 git origin 慢的 bug（Claude Code marketplace 已知问题）
- MANDATORY badge 强制模型先读 SKILL.md 再回答，避免 improvisation 飘移
- metadata.openclaw.optionalEnv 把「按需装配」写到元数据，runtime 按 env 决定能力

**证据**: mvanhorn/last30days-skill v3.3.2（MIT，2026-01-23 创建，3,177 stars today），`SKILL.md` 第 1-30 行 YAML frontmatter + STEP 0 自检；`metadata.openclaw.optionalEnv` 列 11 个可选 key；hooks/scripts/check-config.sh 显式 chmod 600 提示。

**适用场景**: OpenClaw / Hermes 任何想跨 harness 复用的 skill；shared/curated 任何 portable 组件。

**边界**:
- skill 必须有可写方法论契约；纯工具型 skill 不适用
- 必须有 harness Read 多文件能力
- 没有 STEP 0 stale-check 的 harness 不适用（需要 OS-level cache 监测）

**反例**:
- ❌ 写 50 套 platform adapter（codex-plugin / claude-plugin / cursor-extension / opencode-plugin ...）：维护成本爆炸
- ❌ 在 SKILL.md 里直接 `claude code specific API`：迁移成本高
- ❌ 不写 MANDATORY badge：模型 improvisation 概率 5-30%（README 自报 8/8 0 regression）
- ❌ 不检查 stale-clone：cache 落后导致读旧 contract 跑偏

### 79. 跨多 walled-garden 异构源时，应优先用「LLM planner + ThreadPool 并发 + weighted_rrf + Phase 2 反向搜索 + thin source retry」五阶段 pipeline

**经验**: 当需要跨多 walled-garden 异构源（Reddit / X / YouTube / TikTok / Polymarket / GitHub / Bluesky）做统一研究时，应优先用「LLM planner 生成 subqueries + ThreadPoolExecutor 并发 fetch + weighted_rrf 融合 + Phase 2 实体抽取反向搜索 + Phase 2b thin source retry」五阶段 pipeline，而不是串行调用各源 API，因为：
- planner 把「搜什么」和「在哪搜」分离，便于 per-source cap
- 并发 + 429 sharing 让单源 rate limit 不拖垮整次 run
- weighted_rrf 允许给「主 handle」和「related handle」不同权重
- Phase 2 反向搜索把「实体人名」接回 Phase 1 的 source
- Phase 2b retry 让 thin source（<3 results）用简化 query 重试

**证据**: last30days-skill pipeline.py (1138 行)，三个 `_run_*` 函数 + `weighted_rrf` fusion + `entities.extract_entities` 反向搜索 + `_retry_thin_sources` 自动 retry；21,711 行 lib/ 适配 16 个 walled-garden。

**适用场景**: Hermes 多源研究（GitHub + GitLab + npm + PyPI）；OpenClaw 任何「跨平台聚合」任务（搜索跨 Slack + Discord + Telegram）；任何 LLM + 多源的研究型 agent。

**边界**:
- 必须有 LLM planner；纯 deterministic 检索不适用（直接走 SQL）
- 单源足够时（just GitHub）不适用（过度工程）
- walled-garden 必须可 API 化（无法绕过 CAPTCHA）

**反例**:
- ❌ 串行调用各 API：单源失败 → 整次 run 失败；总耗时 = sum(每源延迟)
- ❌ 没有 429 sharing：单源 rate limit 触发后其它源继续打 → 雪崩
- ❌ 没有 Phase 2 反向搜索：实体人名只匹配字面，漏掉「Peter Steinberger = steipete」
- ❌ 没有 retry：thin source 永远 thin，结果不平衡

### 80. 高读低写 Rust 索引应优先用「4 个 OnceLock<Vec<T>> + add 时 OnceLock::new() 替换」而不是 Arc<RwLock<>>

**经验**: 当 Rust 数据结构需要 lock-free 高 QPS read + 偶尔 mutation 时，应优先用「4 个 `OnceLock<Vec<T>>` 缓存 rotation/boundaries/centroids/blocked + add 时直接 `self.blocked = OnceLock::new()` 替换」而不是 `Arc<RwLock<>>` 或 `Mutex<>`，因为：
- `search(&self)` 不用锁；第一次 caller 付 init 成本，后续 caller lock-free read
- `add(&mut self)` 已经独占写权限，OnceLock 替换是 O(1)
- 比 Mutex 跨线程读性能高一档（无 contention）
- 比 Arc<RwLock<>> 代码更简单（无 Arc 引用计数）

**证据**: turbovec lib.rs `pub struct TurboQuantIndex`（1138 行），4 个 `OnceLock<...>`：`rotation: OnceLock<Vec<f32>>`, `boundaries: OnceLock<Vec<f32>>`, `centroids: OnceLock<Vec<f32>>`, `blocked: OnceLock<BlockedCache>`；`add()` 末尾 `self.blocked = OnceLock::new()` 失效。

**适用场景**: OpenClaw 任何「构建昂贵、查询廉价」的索引（VaultLoader cache / GitHub repo metadata cache / Embedding cache）；Hermes 任何类似结构。

**边界**:
- 初始化必须确定性（不能依赖运行时数据），否则不能 OnceLock 缓存
- mutation 必须有 `&mut self` 独占路径；并发 mutation 不适用
- 单线程场景不适用（直接 lazy init 即可）

**反例**:
- ❌ 用 `Arc<RwLock<HashMap>>`：读时 acquire read lock，每次都付锁成本
- ❌ 用 `Mutex<Vec<f32>>`：读阻塞写，QPS 上不去
- ❌ 每次 search 都重新计算 rotation：性能浪费

### 81. 当 embedding 来自不可信输入时，应优先显式校验 NaN/Inf/Huge-magnitude 而不是 silent corruption

**经验**: 当 Rust API 接不可信 embedding 输入（用户上传 / 第三方 API / 多源聚合）时，应优先显式校验 NaN/Inf/Huge-magnitude 并 panic 或返回 typed error，而不是 silent corruption，因为：
- `0 * NaN = NaN` 会毒化整个 SIMD batch，silent 失败
- `MAX_INPUT_MAGNITUDE = 1e16` 防 f32 sum-of-squares overflow to Inf
- `add()` panic + `add_2d()` 返回 typed `AddError::InvalidInputValue` 让 Python 端能 `try/except`
- 比 try/except on fire 省事，比「skip invalid silently」安全

**证据**: turbovec lib.rs `first_invalid_coord()`（40 行）+ `MAX_INPUT_MAGNITUDE: f32 = 1e16`；PyO3 binding `pyo3::exceptions::PyValueError::new_err` 显式抛错。

**适用场景**: OpenClaw 任何 embedding ingest 路径（user 上传 .npy / 第三方 API 转发 / multi-source 聚合）；Hermes 任何 RAG 向量写入；任何 ingest pipeline。

**边界**:
- trusted 内部分支可以省（性能敏感时）
- 不是 f32 而是 f64 时 `MAX_INPUT_MAGNITUDE` 需要重新算
- 不是 Rust 而 Python 时可以用 numpy `np.isfinite() + np.abs() < threshold` 组合

**反例**:
- ❌ 静默 skip：用户不知情，recall 莫名其妙掉
- ❌ `unwrap()` or default value：NaN → 0.0 让 score 计算完全乱
- ❌ 不检查 magnitude：f32 sum-of-squares overflow 到 Inf → top-k 永远返回溢出 vector

### 82. Vault-style app 优先用「Filesystem as SoT + Cache layer + Disk-first invariant + Identity-matched cache reuse」四件套防崩溃

**经验**: 当构建 vault-style app（笔记 / memory / 文档 / 学习记录）时，应优先用「Filesystem as single source of truth + Cache layer（可删）+ Disk-first invariant + Identity-matched cache reuse (modifiedAt + fileSize)」四件套防崩溃一致性，而不是把 state 全放 SQLite 或 IndexedDB，因为：
- 用户期待「这个 app 关了/崩了数据还在」
- Cache layer 只为启动加速，可删；不存 source of truth
- Disk-first invariant 保证 React state 不领先 disk（崩溃可恢复）
- Identity-matched cache（`byte_len + content_hash`）比单纯 mtime 更可靠（git checkout 不更新 mtime 但 content 变了）

**证据**: tolaria ARCHITECTURE.md「Three representations, one authority」+ 5 invariants；`vault/cache.rs` `CacheFileFingerprint { byte_len, content_hash }`；`CACHE_VERSION: u32 = 14` 字段变更强制全 rescan。

**适用场景**: OpenClaw daily learning 输出（已写 markdown file 但无 cache）；Hermes memory store；任何「app 关闭后数据必须还在」的笔记类 app。

**边界**:
- 写入吞吐受 disk IO 限制；纯实时协作场景不适用（需要 CRDT + OT）
- cache layer 仅加速启动，不替代 source of truth
- 跨进程 atomic write 需要 write-then-rename（tolaria 隐含做但 ARCHITECTURE.md 未明示）

**反例**:
- ❌ 把 state 全放 IndexedDB / SQLite：用户换浏览器 / 重置系统就丢
- ❌ Cache 比 disk 优先：cache 与 disk 不一致就报错
- ❌ 不验证 cache identity：mtime 不更新导致 stale 数据
- ❌ 不 bump CACHE_VERSION：字段变了但 cache 还用旧 schema，反序列化失败
