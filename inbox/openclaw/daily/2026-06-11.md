### 解决的问题

- 替代「**通用 agent 写 SKILL 跑 code review**」的脆弱做法：覆盖不全、位置漂移、提示词微调即质量波动。
- 让 code review 的"**必须不出错的步骤**"（文件选择、bundling、规则匹配、定位、反思）由**确定性 Go 代码**保证，把"**需要判断的步骤**"（场景 prompt、动态上下文）交给 LLM agent。

#### 代码块 2: `Tool` 抽象 + 可冻结 `Registry`（`internal/tool/definitions.go` L7-72）

```go
var (
    Unknown      = Tool{name: "unknown"}
    TaskDone     = Tool{name: "task_done"}
    CodeComment  = Tool{name: "code_comment"}
    FileRead     = Tool{name: "file_read"}
    FileFind     = Tool{name: "file_find"}
    FileReadDiff = Tool{name: "file_read_diff"}
    CodeSearch   = Tool{name: "code_search"}
)

type Provider interface {
    Tool() Tool
    Execute(ctx context.Context, args map[string]any) (string, error)
}

type Registry struct {
    providers map[string]Provider
    frozen    bool
}

func (r *Registry) Register(p Provider) {
    if r.frozen {
        panic("tool: Register called on frozen registry")
    }
    r.providers[p.Tool().name] = p
}

func (r *Registry) Freeze() { r.frozen = true }
```

**逻辑摘要**：
- 7 个 `Tool` 全部是包级变量（不是 type+instance）——这是 Go 里"轻量 enum + 零分配" 的惯用法（和 Rust 的 `OnceLock` 思路类似）。
- `Provider` interface 只暴露 `Tool()` 标识 + `Execute()` 执行；**没有 `Schema()`**（schema 在 `toolsconfig/tools.json` 单独维护，LLM 侧只关心 JSON Schema）。
- `Freeze()` 是显式不变性开关：`Register` 后调 `Freeze()`，之后任何 `Register` 都 panic。这是**单元测试不友好但生产安全**的模式（启动期一次性装配，运行时只读）。

#### 代码块 3: `CommentWorkerPool` 后台池（`internal/agent/agent.go` L138-188）

```go
type CommentWorkerPool struct {
    semaphore chan struct{}
    wg        sync.WaitGroup
    resultsMu sync.Mutex
    results   []model.LlmComment
}

func NewCommentWorkerPool(workerCount int) *CommentWorkerPool {
    if workerCount <= 0 { workerCount = 8 }
    return &CommentWorkerPool{semaphore: make(chan struct{}, workerCount)}
}

func (p *CommentWorkerPool) Submit(f func() ([]model.LlmComment, error)) {
    p.wg.Add(1)
    go func() {
        defer p.wg.Done()
        p.semaphore <- struct{}{}        // acquire
        defer func() { <-p.semaphore }() // release
        comments, err := f()
        if err != nil { /* log to stdout writer */ }
        p.resultsMu.Lock()
        p.results = append(p.results, comments...)
        p.resultsMu.Unlock()
    }()
}

func (p *CommentWorkerPool) Await() []model.LlmComment { p.wg.Wait(); return p.results }
```

**逻辑摘要**：
- 经典 semaphore + WaitGroup 模式：每个 Submit 启动 goroutine、acquire semaphore（满则阻塞）、执行 f、release、append 到 results。
- **关键设计**：`Run()` 在 `loadDiffs` 之后调 `a.args.Tools.Freeze()`，再调 `dispatchSubtasks`——保证 worker pool 与 tool registry 的初始化顺序不被并发破坏。
- 对比 Java 端的 `subtaskExecutor`（注释里 L138 提到"mirrors the Java side's subtaskExecutor"），是「Java ExecutorService → Go goroutine + semaphore」的等价物；这给 OpenClaw/Hermes 跨语言实现后台池一个清晰模板。

### 可复用经验

1. 当 LLM 系统需要"必须不出错的步骤 + 需要 LLM 判断的步骤"混合编排时，**应优先采用「Deterministic Engineering × Agent Hybrid」分层**，把 deterministic 部分从 LLM 抽出来用代码实现（文件过滤、bundling、规则匹配、位置校准、反思），LLM 只做动态判断；因为单纯靠 prompt 调优无法稳定 position drift 和 coverage 缺失，**边界**是 deterministic 部分必须可单测，且 LLM 决策要可解释（每条 comment 有 traceable prompt/response）。

2. 当 Go 系统需要"独立子任务并发 + 后台池不阻塞主循环"时，**应优先用「semaphore + WaitGroup + 显式 Freeze()」三件套**，而不是 `errgroup.Group` 或 channel pool；因为 semaphore 模式对 worker 数控制最直接，`Freeze()` 显式标记"启动期装配完成"防止运行时 race，**边界**是 single-process 场景；如果跨进程需要改用 actor 模型。

3. 当解析外部文本格式（如 git diff / log / 配置文件）时，**应优先把 ctx 超时显式包在 `context.WithTimeout` 里**（OCR 用 2 分钟），而不是依赖上游 ctx；因为 `git show <ref>:<path>` 在大 ref / slow IO 时可能 stuck，**边界**是超时不能太短（< 30s）否则正常 ref 也会被打断。

4. 当多 LLM provider 需统一抽象时，**应优先实现「Message/ContentBlock/ToolCall 统一结构 + 各自 SDK 包适配」分层**，不要让上层代码感知 provider 差异；因为 OpenAI 用 `tool_call_id`、Anthropic 用 `tool_use_id`，**边界**是 provider-specific 特性（如 Anthropic cache_control）需要单独字段而非挤进通用 Message。

#### 代码块 1: `runTurn` 单 turn 状态机（`packages/agent-core/src/loop/run-turn.ts` L27-127）

```typescript
export async function runTurn(input: RunTurnInput): Promise<TurnResult> {
  const { turnId, signal, llm, buildMessages, dispatchEvent, tools, hooks, log, maxSteps, ... } = input;
  let usage: TokenUsage = emptyUsage();
  let steps = 0;
  let stopReason: LoopTurnStopReason = 'end_turn';
  let activeStep: number | undefined;

  try {
    while (true) {
      signal.throwIfAborted();
      if (maxSteps !== undefined && maxSteps > 0 && steps >= maxSteps) {
        throw createMaxStepsExceededError(maxSteps);
      }
      steps += 1;
      activeStep = steps;
      const stepResult = await executeLoopStep({ turnId, signal, buildMessages, dispatchEvent, llm, tools, hooks, log, currentStep: steps, maxRetryAttempts, recordUsage: recordStepUsage });
      activeStep = undefined;

      if (stepResult.stopReason === 'tool_use') { continue; }
      const terminalStopReason: LoopTerminalStepStopReason = stepResult.stopReason;
      stopReason = terminalStopReason;
      // 关键钩子：宿主可基于 stopReason/usage 决定是否继续
      const continuation = await hooks?.shouldContinueAfterStop?.({ turnId, stepNumber: steps, usage: stepResult.usage, stopReason: terminalStopReason, signal, llm });
      if (continuation?.continue !== true) { break; }
    }
  } catch (error) {
    if (isAbortError(error) || signal.aborted) { /* interrupted event */ }
    // ... error path
  }
  return { stopReason, steps, usage };
}
```

**逻辑摘要**：
- 单 `while(true)` 循环：每轮 `executeLoopStep` 跑一个 step（LLM → tool），根据 `stopReason` 决定继续或退出。
- `activeStep` 跟踪"中断时正在跑的 step"——给 abort event 提供可观测性（"我在 step 5 被打断的"）。
- `shouldContinueAfterStop` 钩子是**宿主控制** agent 是否继续的关键——比如"端到端用完 → end_turn"，但"goal 模式下 → 自动续命做 goal completion check"。
- `recordStepUsage` 通过 closure 聚合 token 用量，无需返回后再次扫 event 流。

#### 代码块 2: `DefaultToolApprovePermissionPolicy`（`packages/agent-core/src/agent/permission/policies/default-tool-approve.ts` L1-34）

```typescript
const DEFAULT_APPROVE_TOOLS = new Set([
  'Read', 'Grep', 'Glob', 'ReadMediaFile', 'SetTodoList', 'TodoList',
  'TaskList', 'TaskOutput', 'CronList', 'WebSearch', 'FetchURL',
  'Agent', 'AskUserQuestion', 'Skill',
  // Goal control tools have no side effects on the world: GetGoal reads,
  // and mutation tools only record the goal's own runtime state.
  'GetGoal', 'SetGoalBudget', 'UpdateGoal',
]);

export class DefaultToolApprovePermissionPolicy implements PermissionPolicy {
  readonly name = 'default-tool-approve';
  evaluate(context: PermissionPolicyContext): PermissionPolicyResult | undefined {
    if (!DEFAULT_APPROVE_TOOLS.has(context.toolCall.name)) return;
    return { kind: 'approve' };
  }
}
```

**逻辑摘要**：
- **15 个 tool 的白名单**显式列出 "无副作用 / 无 world-changing" 的工具，作为 deny-by-default 的"安全默认"。
- `evaluate` 返回 `undefined` 表示"这条规则不表态，由其他 policy 决定"——**多 policy 链式 evaluate + 第一个返回非 undefined 的 policy 胜出**是典型 chain-of-responsibility。
- 注释 "Goal control tools have no side effects on the world" 揭示了 design 哲学：把 mutation 分成"修改 agent 内部状态"和"修改外部世界"两类，后者才需要 ask。

#### 代码块 3: `FileAccessAskPermissionPolicy` 路径分类（`packages/agent-core/src/agent/permission/policies/file-access-ask.ts` L17-78）

```typescript
export class SensitiveFileAccessAskPermissionPolicy implements PermissionPolicy {
  readonly name = 'sensitive-file-access-ask';
  constructor(private readonly agent: Agent) {}
  evaluate(context: PermissionPolicyContext): PermissionPolicyResult | undefined {
    const access = fileAccesses(context).find((fileAccess) => isSensitiveFile(fileAccess.path));
    if (access === undefined) return;
    return { kind: 'ask', reason: fileAccessReason(access, { sensitive_path: true }) };
  }
}

export class GitControlPathAccessAskPermissionPolicy implements PermissionPolicy {
  readonly name = 'git-control-path-access-ask';
  async evaluate(context: PermissionPolicyContext): Promise<PermissionPolicyResult | undefined> {
    const cwd = this.agent.config.cwd;
    if (cwd.length === 0) return;
    const pathClass = this.agent.kaos.pathClass();
    const accesses = fileAccesses(context);
    if (accesses.length === 0) return;
    // 1. 直查：路径是否包含 .git 组件
    const directGitAccess = accesses.find((fileAccess) => hasGitPathComponent(fileAccess.path, cwd, pathClass));
    if (directGitAccess !== undefined) return { kind: 'ask', reason: fileAccessReason(directGitAccess, { git_control_path: true }) };
    // 2. worktree 探测：cwd 实际 git worktree 的 .git 路径
    const marker = await findGitWorkTreeMarker(this.agent.kaos, cwd);
    if (marker === null) return;
    const access = accesses.find((fileAccess) => isGitControlPath(fileAccess.path, marker, pathClass));
    if (access === undefined) return;
    return { kind: 'ask', reason: fileAccessReason(access, { git_control_path: true }) };
  }
}
```

**逻辑摘要**：
- **`kaos.pathClass()`** 抽象 OS 路径语义（posix vs win32），让后续 `relativePathParts` 自动选 `posixPath` / `win32Path`。
- 两步防御：先看路径字面是否含 `.git`；否则用 `findGitWorkTreeMarker` 走 `git worktree` 探测真实 `.git` 位置（submodule / linked worktree 场景）。
- `policy.evaluate` 支持同步 / async（返回 `Promise | undefined`），多个 policy 顺序 evaluate，第一个非 undefined 胜出。

### 可复用经验

1. 当 agent CLI 需要"声明式 + 可挂载"配置时，**应优先采用「Profile YAML + 4 个内置 profile (agent/coder/explore/plan) + systemPromptPath」模式**，而不是把 system prompt 写死在代码里；因为 agent 行为应该可被最终用户/团队 override 而无需改代码，**边界**是 Profile 必须有 schema 校验（避免 YAML typo 引发 silent miss）。

2. 当 agent 需要"deny-by-default 但无副作用 tool 自动批"时，**应优先采用「PermissionPolicy chain-of-responsibility + 显式白名单 Set」模式**，把所有权限决策集中到 14 个独立 policy class，让 yolo-mode / plan-mode / sensitive-file 等组合成为"policy stack 顺序问题"而非代码路径分支；**边界**是 policy evaluate 必须可观测（log evaluate 过程），否则 silent miss 时 debug 困难。

3. 当 agent 需要"主 agent 控制子 agent 的 approval / question"时，**应优先采用「Reverse-RPC」模式**（`tui/reverse-rpc/approval/`），让子 agent 通过 RPC 把 approval request 反向抛给主 TUI handler，而不是给子 agent 单独开 prompt 阻塞；**边界**是必须设计 abort propagation（子 agent abort 必须能传到主 RPC handler）。

4. 当分发 CLI 工具给非 Node 用户时，**应优先采用「5 阶段 sea-blob 单文件打包 (bundle → sea-blob → inject → sign → verify)」**，让用户 `curl | bash` 一次就能装；因为 Node 部署是 cross-platform 最大障碍，**边界**是 sea blob 受 Node 内部 ABI 限制，跨 Node major 必须重 build。

5. 当 agent 要被外部 IDE（Zed / JetBrains）驱动时，**应优先采用「Agent Client Protocol (ACP) 适配器」**作为桥接，而不是写 IDE 专属 plugin；因为 ACP 是行业标准（agentclientprotocol.com），**边界**是 ACP 能力矩阵未必覆盖所有自定义 tool，需要 graceful degradation。

### 一句话判断

把 Linux `fork(2)` 语义**搬进 KVM microVM**——100 children in 101ms，BRANCH 56ms p50（live mode）；用 memfd + UFFD_WP + diff snapshot chain 三件套实现「agent sandbox 快启 + warm state 继承 + parent 内容哈希校验」；与 Hermes sandbox / OpenClaw runtime sandbox 路线**直接相关**。

### 解决的问题

- 替代「每次 agent 执行都冷启 sandbox」——重复 `pip install numpy`、JIT 编译、模型加载浪费 5-30s。
- 替代「agent 共享同一 OS 进程 + namespace 隔离」——namespace 隔离不够，agent 失控可能击穿 OS。
- 替代「container snapshot = tar 整个 rootfs」——container snapshot 是文件系统级，没有内存状态继承；agent 中途状态丢失。

### 架构 / 实现

**Workspace 4 个 crate + 4 个 experiment PoC**：
- `crates/forkd-vmm`（核心）：Firecracker wrapper + snapshot/fork/branch/chain primitives（2203 行 lib.rs）
- `crates/forkd-uffd`（uffd handler）：Firecracker UDS 握手 + UFFD 事件循环
- `crates/forkd-controller`：HTTP API（axum 0.7 + rustls）+ 鉴权 + audit + state machine
- `crates/forkd-cli`：cobra-style CLI（`fork` / `snapshot` / `branch` / `doctor` / `hub` / `bench`）
- `experiments/v0.4-*-poc/`：4 个独立 PoC（uffd-wp / kvm-uffd-wp / thp-uffd-wp / restore）

**关键子系统**：
- **memfd-backed RAM**（`crates/forkd-vmm/src/memfd.rs`）：把 snapshot 的 `memory.bin` 拷进 memfd，让 vendored Firecracker 能 `mmap(MAP_SHARED)` + `UFFDIO_WRITEPROTECT` 捕获 dirty pages。
- **UFFD handshake**（`crates/forkd-uffd/src/lib.rs`）：Firecracker 在 snapshot-load 时通过 UDS 发送 `(uffd_fd, Vec<GuestRegionUffdMapping>)`，forkd 接收 + 解析 + 喂给 UFFD event loop。
- **Diff snapshot chain**（`crates/forkd-vmm/src/chain.rs`）：每层 snapshot 记 `parent_tag` + `parent_content_hash`；spawn 时从 base 走链装配 `memory.bin`，reflink 优化 cp。
- **Live BRANCH**（`crates/forkd-vmm/src/lib.rs`）：把 source VM pause + memfd 复制异步执行，caller 等 ~10ms 拿 status="writing"，后台 copy 完成后 status="ready"。

**数据流**：
```
parent VM (booted, paused, memfd-backed)
    ↓ forkd fork --tag pyagent
100 children via mmap(MAP_PRIVATE) of parent's memory image
    ↓ 各 child 独立 KVM 进程，CoW 共享 parent 内存页
    ↓ child 写自己的 dirty page → UFFD_WP 捕获 → memfd 后台复制
    ↓ 状态 = 自己的 + parent 的 warm state (numpy, pandas 预加载)
    ↓ agent 跑 ReAct loop
        ↓ 中途 forkd snapshot --from-sandbox <id> --live --no-wait
        ↓ live BRANCH: pause + memfd copy 后台跑
        ↓ 10ms 后 caller 拿 status="writing"
        ↓ ... 几个 subagent 各自 divergent path
        ↓ 但所有继承相同的 prior reasoning
```

#### 代码块 1: `GuestRegionUffdMapping` 兼容 FC wire format（`crates/forkd-uffd/src/lib.rs` L41-87）

```rust
/// Wire-compatible with Firecracker's `GuestRegionUffdMapping`
/// (`src/firecracker/examples/uffd/uffd_utils.rs` in
/// firecracker v1.10.1). When Firecracker connects to our UDS at
/// snapshot-load time it sends one JSON-encoded `Vec<GuestRegionUffdMapping>`
/// (this struct) plus the uffd file descriptor as `SCM_RIGHTS` ancillary data.
#[derive(Debug, Clone, Serialize, Deserialize, PartialEq, Eq)]
pub struct GuestRegionUffdMapping {
    /// Host virtual address where Firecracker mapped this guest region.
    pub base_host_virt_addr: u64,
    pub size: usize,
    /// Byte offset of this region within the backing `memory.bin`.
    pub offset: u64,
    /// Page size of this region in KiB. Firecracker uses 4 KiB pages today.
    pub page_size_kib: usize,
}

impl GuestRegionUffdMapping {
    pub fn contains(&self, host_va: u64) -> bool {
        host_va >= self.base_host_virt_addr && host_va < self.base_host_virt_addr + self.size as u64
    }
    pub fn offset_for(&self, host_va: u64) -> Option<u64> {
        if !self.contains(host_va) { return None; }
        Some(self.offset + (host_va - self.base_host_virt_addr))
    }
}

#[test]
fn region_serde_round_trip_matches_firecracker_wire_format() {
    // Field names and casing must match Firecracker's serialization
    // verbatim — Firecracker uses serde defaults (snake_case). Any
    // rename here breaks the handshake silently.
    let json = serde_json::to_string(&r).unwrap();
    assert!(json.contains("base_host_virt_addr"));
    // ...
    let back: GuestRegionUffdMapping = serde_json::from_str(&json).unwrap();
    assert_eq!(r, back);
}
```

**逻辑摘要**：
- 字段名 `base_host_virt_addr` / `page_size_kib` 必须**逐字符匹配** Firecracker serde 默认输出（snake_case）；注释明确警告"任何 rename 这里会静默破坏 handshake"。
- `contains` / `offset_for` 给出 host VA → memory.bin offset 的翻译；这是 forkd 持有 fds 但 FC 独立映射同一 memfd 的关键转换函数。

#### 代码块 3: `resolve_chain` 链防御（`crates/forkd-vmm/src/chain.rs` L36-94）

```rust
pub const MAX_CHAIN_DEPTH: usize = 32;

/// Walk parents from the chain head down to the base.
/// `lookup` is `tag -> Snapshot` for resolving each parent tag to its metadata.
pub fn resolve_chain<F>(head_tag: &str, lookup: F) -> Result<Vec<(String, Snapshot)>>
where F: Fn(&str) -> Result<Snapshot>,
{
    let mut chain: Vec<(String, Snapshot)> = Vec::new();
    let mut current_tag = head_tag.to_string();

    for _ in 0..=MAX_CHAIN_DEPTH {
        // 关键防御：cycle check (linear scan OK because depth tiny)
        if chain.iter().any(|(t, _)| t == &current_tag) {
            bail!("snapshot chain has a cycle: `{}` is reachable from itself via parent_tag", current_tag);
        }
        let snap = lookup(&current_tag).with_context(|| {
            format!("resolve chain link `{}` (parent of `{}`)", current_tag, chain.last().map(|(t, _)| t.as_str()).unwrap_or(head_tag),)
        })?;
        let next_parent = snap.parent_tag.clone();
        chain.push((current_tag.clone(), snap));
        match next_parent {
            Some(p) => current_tag = p,
            // We hit the base.
            None => { chain.reverse(); return Ok(chain); }
        }
    }
    bail!("snapshot chain for `{}` exceeds MAX_CHAIN_DEPTH={} — use `forkd snapshot compact` to flatten", head_tag, MAX_CHAIN_DEPTH)
}
```

**逻辑摘要**：
- 显式 `MAX_CHAIN_DEPTH=32` + cycle check + missing parent 错误三类防御：防止「用户误创建的深度嵌套链」、「snap A 引用 snap B 引用 snap A 循环」、「删了 parent 但 child 还在」。
- `chain.reverse()` 让结果 base-first 排序，匹配 `assemble_chain_memory` 的消费顺序。
- **`with_context`** 把"我在解析哪条 link"挂在错误上，方便 debug（错误消息会显示 "resolve chain link `py-sklearn` (parent of `py-pandas`)"）。
- 注释警告 "Use `forkd snapshot compact` to flatten" 给出**修复路径**，不只是报错。

### 可复用经验

1. 当需要"快启 sandbox + warm state 继承"时，**应优先采用「memfd + UFFD_WP + diff snapshot chain」三件套**（forkd 哲学），避免每次 cold-boot 浪费时间；因为 warm state（Python imports / JIT 编译 / 模型加载）是 5-30s 级别的优化空间，**边界**是必须有 Linux 5.7+ + KVM + uffd 支持，云端 / WSL 默认不一定满足。

2. 当多 agent fan-out 需要"parent 状态共享 + 独立 KVM 隔离"时，**应优先采用「mmap(MAP_PRIVATE) CoW + vendored Firecracker fork」组合**，而不是 container snapshot（无内存继承）或 cgroup-only（共享 OS 进程）；**边界**是 vendored fork 维护成本高，单纯 sandbox 需求可先用 container。

3. 当构建 snapshot chain 时，**应优先显式「MAX_CHAIN_DEPTH + cycle check + missing parent error」三件套**（forkd 用 32 + linear scan cycle + with_context error），因为"子引用错位"是非常常见的 silent corruption 来源，**边界**是 deep chain 应该用 `snapshot compact` 主动 flatten。

4. 当 fork() 语义跨进程时，**应优先用「`forkd spawn` + `--live` + `--no-wait`」实现 fire-and-forget BRANCH**（caller 10ms 返回，后台 copy 异步完成），而不是同步等结果；因为 agent loop 的"分叉思考"不能被 sandbox 启动阻塞，**边界**是必须显式 poll `status="ready"` 后才能用 child，否则会拿到半成品。

5. 当设计外部数据契约（如 Firecracker UDS 协议）时，**应优先把字段名 + casing + 序列化方向写在 module doc comment + 单测里**（forkd `region_serde_round_trip_matches_firecracker_wire_format` test），因为"上游默默改字段名"是最难 debug 的破坏来源。

## 经验沉淀（3 项目级 + 5 通用 = 8 条）

### 项目级经验

1. **alibaba/open-code-review**：当 LLM 系统需要"必须不出错的步骤 + 需要 LLM 判断的步骤"混合编排时，**应优先采用「Deterministic Engineering × Agent Hybrid」分层**（OCR 哲学），因为纯 prompt 调优无法稳定 position drift / coverage 缺失；**边界**是 deterministic 部分必须可单测。

2. **MoonshotAI/kimi-code**：当 agent CLI 需要"声明式 + 可挂载"配置时，**应优先采用「Profile YAML + Permission Policy chain + Reverse-RPC + ACP」四件套**（kimi 哲学），让 agent 行为 / 权限 / 通信 / IDE 桥接全部声明化；**边界**是必须 schema 校验 + 可观测 evaluate。

3. **deeplethe/forkd**：当需要"快启 sandbox + warm state 继承"时，**应优先采用「memfd + UFFD_WP + diff snapshot chain + live BRANCH fire-and-forget」组合**（forkd 哲学），因为 5-30s 的 warm state 是巨大优化空间；**边界**是 Linux 5.7+ + KVM + uffd 硬要求。

### 跨项目通用经验

4. **当 Go 系统需要独立子任务并发 + 后台池不阻塞主循环时，应优先用「semaphore + WaitGroup + 显式 Freeze()」三件套**（来自 OCR `CommentWorkerPool` + `tool.Registry`），比 `errgroup.Group` / channel pool 控制更直接；**边界**是 single-process 场景。

5. **当 agent 需要 deny-by-default 但无副作用 tool 自动批时，应优先采用「PermissionPolicy chain-of-responsibility + 显式白名单 Set」模式**（来自 kimi-code `DefaultToolApprovePermissionPolicy`），把 14 个 policy 串成 stack，yolo-mode / plan-mode / sensitive-file 变成"policy 顺序"问题；**边界**是 policy evaluate 必须可观测（log）。

6. **当解析外部文本格式（git diff / log / 配置文件）时，应优先把 ctx 超时显式包在 `context.WithTimeout` 里**（OCR 用 2 分钟 + `runner` 共享 limiter），因为 `git show <ref>:<path>` 在大 ref / slow IO 时可能 stuck；**边界**是超时不能太短（<30s）否则正常 ref 也会被打断。

7. **当外部 wire format（如 Firecracker UDS）字段必须逐字符匹配时，应优先把字段名 + casing + 序列化方向写在 module doc comment + 单测里**（forkd `region_serde_round_trip_matches_firecracker_wire_format` test），因为"上游默默改字段名"是最难 debug 的破坏来源；**边界**是单测必须随上游版本回归。

8. **当 fork() 语义跨进程时，应优先用「fire-and-forget + 显式 status 轮询」实现 BRANCH**（forkd `--live --no-wait`，caller 10ms 返回），而不是同步等结果；**边界**是必须显式 poll `status="ready"` 后才能用 child，否则会拿到半成品。
