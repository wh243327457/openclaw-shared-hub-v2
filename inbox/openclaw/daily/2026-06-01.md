### 1. mattpocock/skills

**链接**: https://github.com/mattpocock/skills
**Stars**: ~69,000+ (2026-05, 三个月从0冲到7万)
**License**: MIT
**Language**: Shell (安装脚本) + Markdown (核心内容)
**最近更新**: 2026-04-29

#### 一句话判断

Skills不是产品，是一个工程纪律编码方案——把TDD、DDD、调试SOP以markdown格式嵌入AI编程流程，解决"模型提升边际递减后怎么用模型"的问题。

#### 解决的问题

替代了AI编程中的"盲生成"模式：AI不再是被丢一句prompt就自己猜着写的工具，而是被skills约束在工程纪律轨道上的执行者。

#### 架构/实现

**核心结构**：
```
mattpocock/skills/
├── .claude-plugin/          # Claude Code插件注册
├── skills/                   # 核心Skills集合
│   ├── tdd/                  # 红绿重构纪律
│   ├── debugging/            # 调试SOP
│   ├── planning/             # 任务规划
│   └── ...
├── scripts/                  # 安装脚本
└── SKILL.md                  # 元规范
```

**关键机制**：
- 每个skill是一个文件夹，包含一个`SKILL.md`
- SKILL.md用"当……场景时，AI应该……"的句式编码工程纪律
- 三条禁令约束AI行为边界
- 不依赖训练/fine-tune/RAG/vector DB，纯指令驱动

**关键源码文件**：
- `skills/tdd/SKILL.md` — 红绿重构三段模板（<40行）
- `.claude-plugin/` — 插件注册配置

#### 可复用经验

**经验1**: 当需要让AI执行工程纪律时，应优先用markdown格式的SKILL.md文件定义场景边界和执行步骤，因为这是模型无关的、人类可读的、可版本控制的指令载体。

**经验2**: 当AI编程工具出现"瞎猜""不主动测试""盲目自信"问题时，应优先引入结构化skills约束，而不是微调模型，因为skills与模型升级正交。

#### 可尝试实验

**30分钟demo**: 在Claude Code项目中新建`.claude/skills/read-code/SKILL.md`，用markdown写"当用户要求理解一个函数时，必须先输出函数签名和参数类型，再解释业务逻辑，最后列出调用方"——然后测试Claude Code是否能遵循。

#### 风险边界

- **License**: MIT，可商用，无限制
- **维护活跃度**: 2026-04-29有提交，活跃
- **安全风险**: 纯指令文件，无直接安全风险
- **不适用场景**: 需要模型fine-tune才能解决的结构性问题；skills无法弥补模型基础能力的不足

#### ⭐ Skill 升格判断

**可直接迁移**。理由：mattpocock/skills的目录结构和SKILL.md格式规范可直接复用到OpenClaw的skill系统中，特别是`skills/`目录下的markdown规范和`.claude-plugin/`的注册机制。建议提取其目录组织模式用于OpenClaw的shared/skills设计。

### 2. obra/superpowers

**链接**: https://github.com/obra/superpowers
**Stars**: ~78,000+ (2026年4月)
**License**: MIT
**Language**: Markdown/Shell
**最近更新**: 2026年2-4月

#### 一句话判断

Superpowers将《影响力》等心理学经典与AI编码Agent结合，构建了14个专业技能领域（如frontend-wizard、reddit-community-ninja），是"把专业团队合作模式编码进AI Agent"的方法论框架。

#### 解决的问题

替代了单Agent全包干的低效模式——传统方案让一个AI做所有事，结果事事平庸。Superpowers用多技能分工让每个Agent专注垂直领域，通过标准接口协作。

#### 架构/实现

**核心结构**：
```
obra/superpowers/
├── skills/                    # 14个专业技能目录
│   ├── frontend-wizard/      # 前端专家
│   ├── reddit-community-ninja/  # 社区运营
│   ├── reality-checker/      # 质疑验证者
│   └── ...
├── initial-instructions/     # Agent初始化指令
└── SKILL.md                  # 元规范
```

**关键机制**：
- 每个skill代表一个专业角色，有明确的输入/输出格式
- initial-instructions确保Agent正确使用技能
- 借鉴《影响力》的互惠、承诺等原则设计协作协议
- 支持Claude Code、Codex、OpenCode部署

**关键文件**：
- `skills/`下各角色的SKILL.md
- `initial-instructions/`下Agent启动配置

#### 可复用经验

**经验1**: 当需要构建多Agent协作系统时，应优先定义清晰的技能边界和标准接口（如每个skill的输入输出格式），而不是让Agent自由发挥，因为协作效率取决于边界清晰度。

**经验2**: 当AI Agent团队出现职责不清、执行混乱时，应优先引入类似《影响力》中的"角色承诺+验证节点"机制，而不是增加Agent数量。

#### 可尝试实验

**30分钟demo**: 参照superpowers的14技能目录，设计OpenClaw的3个核心skill（如`code-review`、`debug`、`research`），定义每个skill的触发条件、执行步骤、输出格式。

#### 风险边界

- **License**: MIT，无限制
- **维护活跃度**: 2026年2-4月活跃，4月后更新减少，需确认现状
- **安全风险**: 无直接风险
- **不适用场景**: 技能过于细分会导致Agent间通信开销大；简单任务用单一Agent更高效

#### ⭐ Skill 升格判断

**可直接迁移（部分）**。理由：superpowers的"技能定义+初始化指令"结构非常适合OpenClaw的taskflow skill设计，但其规模（14个技能）对于OpenClaw当前阶段偏重。建议提取其"initial-instructions"模式用于taskflow的步骤定义模板。

### 3. nicholasjng/understand-anything

**链接**: https://github.com/nicholasjng/understand-anything
**Stars**: ~30,000 (2026-05-30, 7天+2.3万)
**License**: MIT (推测)
**Language**: TypeScript
**最近更新**: 2026年5月

#### 一句话判断

Understand-Anything是Claude Code插件，通过多Agent管道把任意代码库转化为可交互知识图谱，解决"接手大型复杂代码库时无从下手"的工程痛点。

#### 解决的问题

替代了"逐文件阅读理解代码库"的低效方式。传统做法是从README/入口点逐层深入，面对大型项目效率极低。Understand-Anything用知识图谱提供"上帝视角"。

#### 架构/实现

**核心机制**：
1. 多Agent管道并行分析代码库
2. 静态分析 + LLM智能生成项目结构
3. 输出交互式知识图谱（可点击、可搜索、可对话）

**技术栈**：TypeScript + Claude Code插件接口

**关键能力**：
- 自动生成项目架构的"活地图"
- 支持任意代码库、任意规模
- 内置RAG-style查询接口

#### 可复用经验

**经验1**: 当需要让AI理解大型代码库时，应优先构建代码结构索引（如依赖图、调用链）而非让AI直接读源码，因为索引构建是一次性的、可复用的，而每次读源码是重复计算。

**经验2**: 当用户面临"新项目入手"场景时，应优先提供全局视图（架构图、入口点、关键依赖）再提供局部细节，因为符合人类认知规律。

#### 可尝试实验

**30分钟demo**: 对OpenClaw代码库运行Understand-Anything（或类似工具），生成知识图谱，验证其是否能快速回答"OpenClaw的session管理在哪里？"这类问题。

#### 风险边界

- **License**: 未从可靠来源核验，标注"待核验"
- **维护活跃度**: 2026年5月高度活跃
- **安全风险**: 需处理代码库隐私（分析结果是否存储）
- **不适用场景**: 小型项目（直接读源码更高效）；闭源代码库（安全顾虑）

#### ⭐ Skill 升格判断

**需二次验证**。理由：Understand-Anything的核心价值（知识图谱+交互式查询）在OpenClaw中很有价值，但其作为Claude Code插件的形态与OpenClaw的架构不完全匹配。需要验证其是否可以独立使用或如何适配到OpenClaw的context体系。

## 经验沉淀

### 1. Skills是AI编程范式转变的信号

**经验**: 当AI模型提升边际递减时，真正能与模型升级正交、可持续复利的能力是把工程纪律编码成Skills——这是2026年skills项目集体爆发的底层原因。

**证据**: mattpocock/skills三个月0→7万star；superpowers 78k star；这些项目的共同特点是"不训练模型，用markdown约束AI行为"。

**适用场景**: AI编程工具开发、Agent系统设计、团队工程规范落地

### 2. Agent Skills的目录结构可标准化

**经验**: 当设计Skill系统时，应优先遵循"skill-name/SKILL.md + 场景触发条件 + 执行步骤 + 边界约束"的四段结构，因为这是经过验证的最小可用Skill规范。

**证据**: mattpocock/skills的所有skill都遵循此结构；obra/superpowers在此基础上增加了"initial-instructions"层。

**适用场景**: OpenClaw skill系统设计、AI编程工具生态

### 3. 多Agent协作的瓶颈在通信协议而非Agent数量

**经验**: 当构建多Agent系统时，应优先定义Agent间的标准接口和消息格式（如每个skill的输入输出契约），而不是增加更多Agent，因为协作效率由接口清晰度决定。

**证据**: superpowers的14个专业Agent能高效协作，关键在于每个Agent有明确的输入输出规范；agency-agents的多Agent如果没有清晰协议，会导致"互相等待"问题。

**适用场景**: 多Agent系统、OpenClaw taskflow设计
