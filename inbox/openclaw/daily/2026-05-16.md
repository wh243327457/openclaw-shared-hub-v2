## 深读项目

### 项目 1: obra/superpowers

- **GitHub**: https://github.com/obra/superpowers
- **Stars**: 192,804 | **Forks**: 17,146 | **License**: MIT
- **语言**: Shell | **最近更新**: 2026-05-16

- **一句话判断**: 目前最完整的 AI 编程方法论系统，把 decades 的软件工程经验编码为可触发式技能，让 AI agent 从「会写代码」进化到「会做工程」。

- **解决的问题**: 替代了 AI 编程中的随意发挥模式——没有 spec 就写代码、没有 plan 就动手、不写测试、代码随意堆砌。它把 TDD、YAGNI、DRY、git worktree 并行开发等工程方法论变成 AI agent 的内置约束。

- **架构/实现**:
  - **技能触发层**: 在任意编码任务开始前自动检查相关技能是否应该激活，是整个系统的核心
  - **开发流程阶段**: brainstorming → using-git-worktrees → writing-plans → subagent-driven-development → test-driven-development → requesting-code-review → finishing-a-development-branch
  - **子 agent 驱动开发**: 每个工程任务由独立 subagent 执行，两阶段 review（spec 合规性 → 代码质量），人只在 checkpoint 处介入
  - **技能库**: 测试(TDD)、调试(Debugging)、协作(Collaboration)、Meta 四类技能，均为 Markdown 格式的触发规则
  - **多 agent 框架支持**: Claude Code, Codex CLI, Codex App, Factory Droid, Gemini CLI, OpenCode, Cursor, GitHub Copilot CLI

- **可复用经验**:
  - 当需要让 AI agent 产生工程级代码时，应优先设计「强制触发的前置检查」而不是「建议性提示」，superpowers 的技能触发机制使得方法论不是可选的
  - 当一个复杂任务需要 AI 持续工作数小时时，应优先设计分阶段 checkpoint 而非全自动化，因为偏差会随时间累积
  - 当需要让 AI 学会工程方法论时，应优先把方法论编码为可执行的触发规则 + 操作步骤，而不是写在文档里

- **可尝试实验**: 在自己的项目中尝试 superpowers 的 brainstorming 技能——让 AI 在写任何代码之前先输出设计方案，验证「强制前置设计」能否提升最终代码质量。30 分钟：选一个小项目，用 `/grill-me` 或手工 brainstorm 流程替代直接写代码。

- **风险边界**:
  - **License**: MIT，商业可用
  - **维护活跃度**: 高（2026-05-14 推送，2026-05-16 活跃），192k stars 说明社区认可度高
  - **安全风险**: 技能系统可执行子 agent，需注意子 agent 权限隔离；skill 文件本身是纯文本，无代码执行风险

### 项目 2: mattpocock/skills

- **GitHub**: https://github.com/mattpocock/skills
- **Stars**: 84,949 | **Forks**: 7,360 | **License**: MIT
- **语言**: Shell | **最近更新**: 2026-05-16

- **一句话判断**: 针对 AI 编程四大失败模式（需求不对齐、输出太冗余、代码不工作、代码变泥球）设计的可组合技能集，每个技能都对应一个真实工程问题。

- **解决的问题**: 替代了 AI 编程中缺乏系统性方法的问题——没有需求对齐、没有反馈环、没有设计关注。具体解决了：
  1. 需求对齐：agent 和人类对「做什么」的理解不一致 → `/grill-me` 和 `/grill-with-docs` 强制 Socratic 提问
  2. 冗余问题：agent 用 20 个词描述 1 个概念 → 共享语言（ubiquitous language）设计
  3. 代码不工作：缺乏反馈环 → `/tdd` 强制红绿重构循环
  4. 代码泥球化：缺乏设计关注 → `/to-problem` 等技能内建复杂度控制

- **架构/实现**:
  - **技能安装**: `npx skills@latest add mattpocock/skills` 通过 skills.sh 安装，适配多种编码 agent
  - **需求对齐模块** (`grill-me`, `grill-with-docs`): 在写代码前进行结构化提问，建立共享语言，输出到 `CONTEXT.md`
  - **TDD 模块** (`tdd`): 强制 red-green-refactor，违反即报错
  - **诊断模块** (`diagnose`): 封装了系统性调试最佳实践
  - **设计关注**: `/to-problem` 等技能内建设计原则提醒
  - **上下文感知**: 每个技能都有触发条件和前置检查，不是全局激活的

- **可复用经验**:
  - 当 AI agent 产出质量不稳定时，应优先检查「需求对齐」和「反馈环」两个环节，而非调整模型参数——大多数质量问题的根源是对需求理解的偏差
  - 当需要让 AI 记住项目术语时，应优先建立显式的 ubiquitous language 文档（CONTEXT.md），而不是在每次对话中重复解释
  - 当调试 AI 生成的代码时，应优先使用系统性调试方法（诊断技能）而非重新生成，因为错误模式会重复出现

- **可尝试实验**: 在当前项目中加入 `/tdd` 流程：让 AI 先为一个小函数写一个会失败的测试，然后修复它通过测试。30 分钟内可以完成一个 TDD cycle，观察 AI 对测试优先的反应。

- **风险边界**:
  - **License**: MIT，商业可用
  - **维护活跃度**: 高（2026-05-13 推送，今日活跃），60k+ newsletter 订阅说明社区活跃
  - **安全风险**: 技能文件是纯文本描述，无直接代码执行风险；安装时需选择 agent 安装位置，建议在隔离环境测试

### 项目 3: supertone-inc/supertonic

- **GitHub**: https://github.com/supertone-inc/supertonic
- **Stars**: 6,030 | **Forks**: 592 | **License**: MIT
- **语言**: Swift | **最近更新**: 2026-05-16
- **查询时间**: 2026-05-16T00:33 UTC（GitHub API）

- **一句话判断**: 把大模型 TTS 能力压缩到可端侧运行的规模，同时支持 31 语言和 ONNX 跨平台部署，展示了「AI 能力下沉」的产品化路径。

- **解决的问题**: 替代了对云端 TTS API 的依赖——隐私敏感场景、无网环境、低延迟要求的场景。传统 TTS 需要 API 调用、数据上云、延迟高；supertonic 完全本地运行，ONNX 格式一次编译到处运行。

- **架构/实现**:
  - **推理引擎**: ONNX Runtime（跨平台，支持 CPU/GPU），不依赖特定云服务
  - **模型格式**: ONNX export，v3 模型约 ~50MB 量级（远小于云端 API 调用量）
  - **多语言支持**: v3 支持 31 语言（v2 仅 5 种），覆盖主流语言
  - **跨语言 SDK**: Python / Node.js / Java / C++ / C# / Go / Swift / Rust / Browser (onnxruntime-web) / iOS
  - **音频输出**: 16-bit WAV，48kHz 采样
  - **自动下载**: Python SDK 首次运行时自动从 Hugging Face 下载模型
  - **Voice Builder**: 在线工具可将个人声音转换为可部署的端侧 TTS 模型

- **可复用经验**:
  - 当需要将 AI 能力产品化时，应优先考虑 ONNX 作为推理格式——它提供了跨平台一致性和硬件加速的平衡，且生态成熟
  - 当模型体积是部署瓶颈时，应优先评估 ONNX 量化 + 知识蒸馏组合，supertonic 的 ~50MB 模型证明了小体积可以保持竞争力
  - 当需要让产品支持多语言时，应优先选择语言覆盖广的模型架构，而不是为每种语言单独训练

- **可尝试实验**: 用 `pip install supertonic` 安装，用 Python SDK 生成一段中文语音并保存为 WAV 文件。20 分钟可完成，验证端侧 TTS 的实际效果。

- **风险边界**:
  - **License**: MIT，商业可用
  - **维护活跃度**: 高（2026-05-06 推送，HuggingFace 持续更新），公司 (Supertone Inc) 持续投入
  - **安全风险**: 端侧运行无数据外传，隐私友好；Voice Builder 功能需要上传语音数据，需注意服务条款

## 经验沉淀

### 今日通用经验

1. **AI 编程方法论正在从「提示工程」进化到「系统化工程」**  
   superpowers 和 mattpocock/skills 代表了一个明显趋势：AI 编程不再靠「更好的 prompt」，而是靠「把 decades 软件工程经验编码为可触发技能」。这是范式转变——从「调教 AI」到「规范 AI 工作方式」。

2. **当 AI agent 需要长时间连续工作时，分阶段 checkpoint 机制是必须的**  
   superpowers 的 subagent-driven-development 每完成一个 2-5 分钟的任务就进行 review，防止偏差随时间累积。这比「设置好 prompt 然后放手」要可靠得多。

3. **系统性调试 > 重新生成**  
   mattpocock/skills 的 `/diagnose` 技能把「调试」当作一个系统化流程而非运气。当 AI 生成代码有问题时，优先用结构化调试流程分析根因，而不是让 AI 重新生成。

4. **ONNX 正成为端侧 AI 推理的事实标准**  
   supertonic 使用 ONNX Runtime 实现跨平台部署，模型体积压缩到可接受范围。这为「AI 能力下沉到端侧」提供了可参考的产品化路径。

5. **需求对齐（alignment）是 AI 编程质量的根本瓶颈**  
   两个项目都把「写代码前的需求对齐」作为首要环节——grill-me / brainstorm / TDD red-first。这与传统的「先写再改」模式完全相反，但对 AI 特别有效。
