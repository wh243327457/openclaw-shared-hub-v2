## 深读项目

### 项目 1: colbymchenry/codegraph

- **一句话判断**: 将 AI 代码探索从"文件扫描"变为"图谱查询"，实测降低 70% 工具调用，是目前 AI 代码理解领域性价比最高的中间件。
- **解决的问题**: AI 代理探索大型代码库时，通过大量 grep/find/Read 子代理发现代码，消耗大量 token 和时间。CodeGraph 预建索引后，代理只需查询图谱即可定位代码。
- **架构/实现**:
  - **索引层**: 使用 FSEvents/inotify/ReadDirectoryChangesW 监听文件变化，增量更新 SQLite 图谱数据库
  - **图谱内容**: 符号关系、调用图、代码结构；支持 19+ 语言；框架感知路由（识别 14 个 Web 框架的路由文件）
  - **查询接口**: MCP server + codegraph_context / codegraph_explore 两个核心工具调用
  - **Benchmark 结果**: VS Code (35% 成本 ↓, 73% tokens ↓, 72% tool calls ↓)；Tokio (52% 成本 ↓, 81% tokens ↓, 89% tool calls ↓)
- **可复用经验**:
  - 当需要让 AI 代理高效理解大型代码库时，应优先建立代码索引而不是依赖动态扫描
  - 当代理倾向于将任务委托给子代理探索时，应直接提供索引查询能力以消除子代理的文件扫描开销
- **可尝试实验**: 对任意 500+ 文件的项目运行 `npx @colbymchenry/codegraph` 建立索引，观察 AI 回答架构问题的工具调用变化
- **风险边界**: License: MIT；100% 本地运行无数据泄露风险；维护活跃度极高（今日 4,294 stars）；但 SQLite 图谱在高并发写入场景可能成为瓶颈

### 项目 2: Imbad0202/academic-research-skills

- **一句话判断**: 首个将"AI 辅助科研写作"系统化为多代理流水线且内置可信度审查的工具集，直接回应了 AI 生成论文的 citation hallucination 问题。
- **解决的问题**: 传统 AI 写作工具不解决引用幻觉问题，生成的论文存在虚假引用和逻辑断层。ARS 通过多阶段代理流水线 + 7 模式 integrity gate 将可信度内化为工作流的一部分。
- **架构/实现**:
  - **Deep Research**: 13 agent 团队，含 Socratic 引导、PRISMA 系统评审、意图检测、对话健康监控
  - **Academic Paper**: 12 agent 写作，含 Style Calibration（学习用户写作风格）、Writing Quality Check（检测机器生成感）、LaTeX 加固、可视化、VLM 图验证
  - **Reviewer**: 7 agent 多视角评审（EIC + 3 动态评审 + Devil's Advocate），含 R&R 可追溯矩阵
  - **Pipeline**: 10 阶段编排器，含自适应检查点和 claim-level 引用审计（L3 层）
  - **引用审计**: v3.8 新增 CLAIM_AUDIT 模式，抓取引文源并判断 claim 是否被实际支持，5 个 HIGH-WARN 类拒绝输出
- **可复用经验**:
  - 当构建涉及外部知识引用的 AI 系统时，应优先将引用可信度检查作为硬 Gate 而非软建议
  - 当使用多代理流水线处理长文本生成任务时，应在中间阶段插入风格校准和逻辑一致性检查
- **可尝试实验**: 用 `/ars-lit-review "LLM 在科研中的应用"` 运行一次文献综述，观察引用溯源流程
- **风险边界**: License: CC BY-NC 4.0（禁止商业使用）；依赖 Claude Code + Anthropic API；Zhao et al. (2026) 发现 146,932 条虚假引用的问题在论文级别仍存在，ARS 只能降低风险不能根除

### 项目 3: ChromeDevTools/chrome-devtools-mcp

- **一句话判断**: 将 Chrome DevTools 封装为 MCP server，让 AI 编程代理能控制真实浏览器进行自动化、调试和性能分析，是浏览器自动化从脚本时代进入 Agent 时代的关键基础设施。
- **解决的问题**: 现有浏览器自动化方案（Selenium/Puppeteer）需要人工操作或复杂脚本；AI 代理无法直接获取浏览器内部状态。chrome-devtools-mcp 通过 CDP 协议让 AI 原生控制浏览器。
- **架构/实现**:
  - **核心**: 基于 Puppeteer 连接真实 Chrome 实例，通过 CDP 协议暴露 DevTools 能力
  - **工具集**: 网络请求分析、截图、控制台消息（含 source-map 解析）、性能 trace 录制、CrUX 真实用户数据
  - **部署**: npx 启动，无需安装，配置简单；支持 Claude Code / Codex / Copilot / Cline 等所有主流 AI 编程代理
  - **Slim 模式**: 轻量级工具子集，适合简单浏览器任务
  - **数据注意**: 默认发送使用统计到 Google，可通过 `--no-usage-statistics` 关闭
- **可复用经验**:
  - 当需要让 AI 代理验证 Web 应用的 UI 行为时，应优先考虑让 AI 直接控制浏览器而非解析 HTML
  - 当 AI 代理需要操作复杂前端应用时，应利用 MCP 协议封装领域特定工具以保持代理接口一致性
- **可尝试实验**: 配置 Claude Code MCP 连接 chrome-devtools-mcp，命令 AI 对任意网页截图并检查 console 错误
- **风险边界**: License: 未知；依赖 Google Chrome 官方稳定版（不支持非 Chromium 浏览器）；性能工具默认上传 trace URL 到 Google CrUX API；数据收集默认开启需注意隐私

## 经验沉淀

1. **索引即性能**: 在 AI 代理场景中，"预建索引 + 查询" 的范式比 "动态搜索 + 读取" 在工具调用效率和 token 消耗上都有数量级优势（70% 工具调用减少）。任何需要 AI 高频理解代码的场景都应优先考虑此模式。

2. **多代理流水线的质量门控**: academic-research-skills 的 7 模式 integrity gate 和 claim-level 引用审计是很好的示范：在创意生成流程中插入可信度检查 Gate，比事后人工审查效率高得多，且可追溯。

3. **MCP 协议正在成为 AI 代理工具扩展的事实标准**: chrome-devtools-mcp 和 codegraph 都通过 MCP 协议暴露能力，这种"协议即中间件"模式让工具可以跨代理复用，值得优先学习 MCP 的工具封装方式。
