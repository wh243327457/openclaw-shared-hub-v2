# 微信推送消息模板 v3

## 定位

这不是“流程字段堆叠”，而是一份用户早上能快速吸收的学习复盘。

目标：用户不打开知识库，也能知道：
1. 今天学习主线是什么
2. OpenClaw 学了哪些项目
3. 哪些项目值得关注，为什么
4. 哪些经验能迁移到当前体系
5. Hermes 如何审计和判断
6. 明天应该继续追什么

## v3 核心原则

### 1. 第一屏先给价值，不先报流程

开头必须先给“今日一句话结论”，让用户马上知道今天学习有没有价值。

不要用：
- “今日学习计划：……”开头
- “审计得分：……”开头

应该用：
- “今天主线是：AI 工具链正在从能用走向工程化。”
- “今天最值得关注的是 uv，因为它给了我们工具链迁移的样板。”

### 2. 项目表格必须是价值导向

表格列固定为：

```
| 项目 | 为什么值得看 | Hermes 判断 | 可沉淀点 |
```

禁止退回：

```
| # | 项目 | 简介 | 亮点 |
```

因为“简介/亮点”偏项目介绍，“为什么值得看/Hermes 判断/可沉淀点”才对用户有决策价值。

### 3. 必须有 Hermes 主观意识

推送不是 OpenClaw 报告的压缩版，Hermes 必须表达判断：

- 哪个项目最值得继续追
- 哪个点能迁移到共享中台 / Agent 工作流 / DevOps / 工具链
- OpenClaw 哪里学得认真
- OpenClaw 哪里学浅了，明天要加压

### 4. 情绪表达要基于审计事实

不要机械地根据项目数量表达情绪。应结合：

| 判断依据 | 表达 |
|---|---|
| 数量达标 + 内容深入 + 有可沉淀点 | “今天有点惊喜” |
| 数量达标但内容浅 | “数量够了，但说实话有点浮” |
| 数量少但质量高 | “虽然少，但质量不错” |
| 缺关键源码/风险/可迁移经验 | “OpenClaw 今天有点糊弄，需要加压” |
| 发现与用户长期系统相关的项目 | “这个值得单独拆一次” |

### 5. 审计结果要解释“为什么”

不能只写得分。至少包含：

- 来源完整
- 技术深度
- 可迁移价值
- 风险边界
- 不足 / 明日加压点

### 6. 可沉淀判断要分级

判断值建议：

- ✅ 立即沉淀
- 🟡 继续观察
- ❌ 暂不沉淀

每条必须说明原因。

## 生成规则

### 今日主线生成

从 OpenClaw 学习报告的“今日结论”“经验沉淀”和深读项目中提炼共同主题。

示例：

- hermes-agent + uv + ollama → “AI 工具链正在从能用走向长期可持续、可部署、可复用。”
- vLLM + SGLang + TensorRT-LLM → “LLM 推理正在从框架选择进入生产优化阶段。”
- Turborepo + Nx + Moonrepo → “前端/全栈 monorepo 工具链正在向缓存和远程执行收敛。”

### Hermes 判断生成

每个项目至少给一句主观判断，格式不限，但必须包含“和用户/系统的关系”。

好例子：
- “和我们共享中台/持续上下文方向高度相关，这个值得继续深挖。”
- “这是旧生态工具链重构的标杆案例，适合迁移到我们未来 CLI 改造里。”

差例子：
- “值得学习。”
- “项目很火。”
- “功能强大。”

### 明日建议生成

明日建议必须来自今日学习结果，而不是固定话术。

必须包含：
- 继续追踪方向
- 原因
- 一个最小动作

## 禁止事项

- ❌ 不要只说“详见知识库”
- ❌ 不要只列审计优点
- ❌ 不要把 OpenClaw 原文机械压缩
- ❌ 不要缺少 Hermes 主观复盘
- ❌ 不要把项目表格写回“简介/亮点”
- ❌ 不要没有情绪、没有判断
- ❌ 不要生成太长的项目背景介绍
- ❌ 不要把所有项目等权展示；必须突出最值得看的 2-3 个
