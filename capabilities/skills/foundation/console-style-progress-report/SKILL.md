# 总控台式进度汇报

## 噪音控制：只汇报实质进展

当用户表达“不要发没用的消息 / 我需要实质性进展 / 继续做”时：
- 不要把平台保护、限流提示、会话刷新提醒、内部运行状态当作用户-facing 进展推送。
- 只有在这些问题会阻塞当前任务、需要用户动作时，才放到“需要你动作/决策”区块。
- 默认继续执行可落地动作，并在完成后只汇报：已完成产物、验证方式、当前状态、下一步一个关键决策。
- 避免为了解释而解释；用户要的是结果时，优先给文件路径、配置状态、验证结果。

## 何时使用

出现以下场景时默认启用本 skill：
- 用户问“现在什么情况？”“进度如何？”“做到哪了？”“汇报一下”
- 任务需要多步工具调用，执行时间已经足够让用户需要状态感知
- 状态色发生变化：从绿到黄、从黄到红、或风险解除
- 出现需要用户决策、确认方向、补权限、补资源的时刻
- 需要异步交接，让后来者能快速接住上下文

## 核心原则

1. 先态势，后过程
   - 第一屏先回答“现在什么情况”，不要先说“我做了什么动作”。

2. 先人话，后工具话
   - 先给用户能判断的结论；命令、日志、todo、issue 编号放到后面或详情入口。

3. 先影响，后细节
   - 每个 blocker 都要翻译成：影响什么、风险多大、是否需要用户介入。

4. 为速读而写
   - 短句、短段、小标题、可扫读。

5. 主文只放摘要，细节走真相源入口
   - 主文给判断；文件路径、文档、报告链接给证据。

## 默认骨架

每次汇报至少包含四槽位：
- 当前阶段
- 完成度
- 人话结论
- 下一步

必要时再追加：
- 风险/阻塞
- 需要你决定
## 强制避免无效推送 / 空提醒

当用户要求“推送结果/产物/进展”时，推送内容必须是**实质性结果**，不能把系统重试、限流保护、会话保护、后台 retry、工具中间状态等原样转发给用户。

- 不要发送“正在重试”“微信会话保护”“回复任意内容刷新会话”这类对用户无业务价值的长提醒，除非它是唯一阻塞且需要用户动作。
- 如果微信/iLink 限流或会话保护触发，非关键长消息应优先落盘，并在下一次有实质结果时用一句话说明“因推送保护已落盘”。
- 用户明确抱怨“没用的消息 / 需要实质性进展 / 怎么还是推送这个”时，立刻切换为：只汇报已完成产物、验证结果、阻塞事实和下一步动作；不要再解释内部 retry 细节。
- 对自动化/采集/学习类任务，最终消息优先包含：本轮实际完成、产物路径、验证状态、真实阻塞、需要用户决策；删除过程噪音。

## 决策事项展示

需要用户拍板的事项必须从普通总结中拆出，单独放入“需要你决策”区块；优先使用序列表格展示：决策项、选项、影响、建议、默认动作。

## 状态色定义

- 绿 / 在轨：主路径清晰，无会影响承诺输出的关键阻塞
- 黄 / 有风险：存在阻塞或关键未知，但解决路径已知，ETA 或完整度可能波动
- 红 / 失轨：关键依赖缺失、核心假设失效，或没有新决策就无法按要求交付

如果用了红黄绿，必须给依据。

## 标准步骤

### 第 1 步：先抽取 point-in-time snapshot
汇报不是动作流水，而是当前态势快照。先回答：
- 现在处于哪一阶段？
- 整体是否在轨？
- 最大结果或最大风险是什么？
- 用户现在要不要做决定？

### 第 2 步：先写 2-3 句 TL;DR
默认顺序：
1. 当前状态
2. 关键结果或关键风险
3. 用户动作

不要把工具调用、检索动作、内部待办放在摘要前面。

### 第 3 步：填充四槽位骨架
推荐固定写法：
- 当前阶段：<收集/收敛/执行/验证/整理/完成>
- 完成度：<百分比或阶段描述 + 依据>
- 人话结论：<一句话说清结果/影响/是否在轨>
- 下一步：<动作 + 谁做 + 预计输出/时间>

### 第 4 步：把内部状态翻译成用户可决策信息
翻译原则：
- 待办 -> 阶段
- 调试 -> 风险与处理路径
- 测试 -> 可信度与验证进展
- 等待外部依赖 -> 影响与 ETA 风险
- 讨论方案 -> 用户需要拍板的选项

### 第 5 步：写 blocker 时必须补四件事
每个 blocker 都要说明：
- 它卡在哪里
- 它影响什么
- 当前解决路径是什么
- 是否需要用户介入

### 第 6 步：细节下沉，不污染主文
主文不要直接贴：
- 原始 todo 长清单
- shell 输出
- 长英文句
- 内部状态流
- 原始 debug 过程

如用户需要，再单独给：
- 详情
- 附录
- 文件路径 / 文档链接 / 证据入口

## 模板

### 模板 A：3 行中途汇报
```text
现在情况：<当前阶段>，整体<在轨/有风险/失轨>，完成度<约 X% / 已进入某阶段>。
人话结论：<最重要结果或风险>。
下一步：<我将做什么，何时回报；是否需要你介入>。
```

### 模板 B：标准总控台版
```text
主题：<任务名称>
状态：<绿/黄/红 + 依据>
当前阶段：<收集/收敛/执行/验证/整理/完成>
完成度：<百分比或阶段描述 + 依据>
人话结论：<一句话说清现在是否顺、主要结果、主要影响>
风险/阻塞：<没有则写“暂无关键阻塞”>
下一步：
1. <动作 + 负责人 + 预期输出/时间>
2. <动作 + 负责人 + 预期输出/时间>
需要你决定：<无 / 具体问题>
详情入口：<链接、文件路径、任务入口>
```

### 模板 C：需要用户拍板时
```text
现在情况：<阶段>，整体<黄/红>，卡点在<关键问题>。
人话结论：主体工作已推进到可推进上限，接下来分支取决于<决策项>。
你需要决定：
- 选项 A：<收益 / 成本 / 风险>
- 选项 B：<收益 / 成本 / 风险>
我建议：<推荐项 + 理由>
下一步：你确认后，我按该路线继续推进。
```

### 模板 D：附细节入口但不污染主文
```text
现在情况：<一句话>
人话结论：<一句话>
下一步：<一句话>
详情入口：
- 主文档：<链接/路径>
- 证据：<链接/路径>
- 原始工作项：<链接/路径>
```

## 禁止项

- 开头先播报工具动作
- 把 activity 当 status
- 把 todo list 当总控台
- 百分比假精确
- 只说卡住，不说影响和路径
- 不说明用户是否需要动作
- 原始日志、英文长句、内部缩写过多
- 主文没有真相源入口

## 发送前检查

- [ ] 第一屏是否已回答“现在什么情况”
- [ ] 是否写明在轨 / 有风险 / 失轨
- [ ] 是否明确当前阶段
- [ ] 完成度是否有依据，而不是拍脑袋
- [ ] 人话结论是否说明了对用户的影响
- [ ] 是否写明用户现在需不需要动作
- [ ] 下一步是否具体到动作与预期输出
- [ ] 是否避免暴露原始 todo、日志、命令流
- [ ] 是否提供详情入口
- [ ] 用户只读前 3-5 行能否抓住主结论
- [ ] 文案是否短句、中文、可扫读
- [ ] 若用了红黄绿，是否有判定依据

## 一句话规则

先说“现在什么情况”，不要先说“我做了什么”；固定输出“当前阶段 / 完成度 / 人话结论 / 下一步”。
